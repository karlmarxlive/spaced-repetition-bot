# Бот для подготовки к ЕГЭ по информатике — этап 7: надёжный учебный цикл

Локальный модульный монолит: Django Admin для учителя, Telegram long polling и отдельный процесс планировщика. Учитель создаёт одноразовое приглашение на выбранный курс. Ученик открывает ссылку в личном чате Telegram и регистрируется; учитель отмечает пройденные темы в панели. `/start` без приглашения для нового пользователя отвечает:

> Для регистрации нужна ссылка-приглашение учителя. Попросите её у учителя.

Учитель использует стандартный Django superuser. Ученик не получает Django-аккаунт, пароль или административные права. Курс, темы и банк заданий доступны в Django Admin. Расписание рассчитывается и сохраняется локально. Зарегистрированный ученик получает задания ежедневно в заданное учителем время, отвечает текстом и видит итог занятия. `/review` позволяет начать или продолжить занятие вручную. Очередь и открытое задание сохраняются в базе.

## Требования и установка (PowerShell)

Python 3.14, SQLite из стандартной библиотеки Python. Проверено на Windows с Python 3.14.0. Django 5.2.17 (ветка LTS), aiogram 3.31.0, python-dotenv 1.2.3. Все прямые и транзитивные зависимости закреплены в `requirements.txt`; устанавливайте именно этот файл.

Поддержка Python 3.14: [Django 5.2](https://docs.djangoproject.com/en/5.2/releases/5.2/); сведения об aiogram: [PyPI](https://pypi.org/project/aiogram/).

```powershell
Set-Location D:\projects\spaced-repetition-bot
py -3.14 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip check
```

Если `.venv` уже подготовлено, повторно создавать его не нужно. Активация окружения не требуется: команды используют его Python напрямую.

## Локальные настройки

Существующий `.env` не перезаписывайте. Создавайте его из примера только при отсутствии:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
notepad .env
```

Вставьте токен BotFather в `TELEGRAM_BOT_TOKEN` непосредственно в локальном файле. Не передавайте токен в чат. При необходимости добавьте остальные параметры из `.env.example`. Процесс читает `.env` из корня проекта; реальные переменные окружения имеют приоритет, даже если значение пустое. Подстановки `${...}` отключены, значения секретов читаются буквально. После изменения настроек перезапустите процессы.

- `TELEGRAM_BOT_TOKEN`: требуется для запуска бота и планировщика; пустой токен завершает команду с кодом 1 и понятным сообщением. Панель и автономные тесты работают без него.
- `TELEGRAM_BOT_USERNAME`: необязательное имя бота **без @**, например `MyExamBot`. Нужно только для формирования ссылки в панели; укажите имя того же бота, чей токен используется. При отсутствии или неверном формате панель покажет подсказку вместо ссылки. Django и бот продолжат работать. Запросы к Telegram для создания ссылки не выполняются.
- `DJANGO_SECRET_KEY`: задайте случайную строку. Если ключ отсутствует при локальном `DJANGO_DEBUG=true`, применяется явно небезопасный ключ разработки; при `false` ключ обязателен.
- `DJANGO_DEBUG`: `true`/`false` (также принимаются `1`/`0`, `yes`/`no`); по умолчанию `true`.
- `DJANGO_ALLOWED_HOSTS`: через запятую, по умолчанию `localhost,127.0.0.1,[::1]`.

Для генерации ключа в буфер обмена без вывода в терминал:

```powershell
.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(48))" | Set-Clipboard
```

Вставьте его после `DJANGO_SECRET_KEY=`. `.env`, `.venv`, SQLite, локальные вложения `media/`, кэши и служебные файлы исключены через `.gitignore`.

## Подготовка панели

```powershell
Set-Location D:\projects\spaced-repetition-bot
.\.venv\Scripts\python.exe manage.py check
if (Test-Path db.sqlite3) {
    .\.venv\Scripts\python.exe -c "import sqlite3; from datetime import datetime; from pathlib import Path; target='backup-' + datetime.now().strftime('%Y%m%d-%H%M%S-%f') + '.sqlite3'; source=sqlite3.connect(Path('db.sqlite3').resolve().as_uri() + '?mode=ro', uri=True); destination=sqlite3.connect(target); source.backup(destination); destination.close(); source.close(); print(target)"
    if ($LASTEXITCODE -ne 0) { throw 'Не удалось создать резервную копию' }
}
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py createsuperuser
```

Резервную копию делайте перед обновлением существующей базы; на новой установке пропустите команду копирования. Существующего superuser повторно создавать не нужно. Имя и пароль нового учителя задайте в интерактивном приглашении. Отдельной модели учителя нет. Django хранит timezone-aware даты; `USE_TZ=True`, часовой пояс отображения — `Europe/Moscow`.

Миграция `users.0001` добавляет новые таблицы и не меняет учебный банк или аккаунты учителя. Предыдущие миграции материалов сохранены. Бот самостоятельно миграции не запускает: после обновления выполните `migrate` и перезапустите все три процесса.

## Быстрый запуск одной командой

После установки зависимостей, настройки `.env`, применения миграций и создания superuser запустите из корня проекта:

```powershell
py -3.14 run_dev.py
```

Скрипт автоматически использует Python из `.venv` и запускает панель, бота и планировщик в одном терминале. Откройте [панель учителя](http://127.0.0.1:8000/admin/). Логи всех процессов выводятся в этот терминал; **Ctrl+C останавливает все три процесса**. Если любой процесс завершится, скрипт остановит остальные и вернёт ненулевой код выхода.

Другой порт: `py -3.14 run_dev.py --port 8001`. На Linux/macOS с подготовленным `.venv`: `python3 run_dev.py`.

Панель работает без автоматической перезагрузки: после изменения кода остановите команду и запустите её снова. Скрипт не устанавливает зависимости, не применяет миграции и не изменяет `.env`. Перед запуском остановите ранее запущенные экземпляры бота и планировщика.

## Запуск в трёх терминалах

Терминал 1 — веб-панель:

```powershell
Set-Location D:\projects\spaced-repetition-bot
.\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

Откройте [панель учителя](http://127.0.0.1:8000/admin/) и войдите под superuser.

Терминал 2 — бот:

```powershell
Set-Location D:\projects\spaced-repetition-bot
.\.venv\Scripts\python.exe -m bot
```

Терминал 3 — ежедневная выдача:

```powershell
Set-Location D:\projects\spaced-repetition-bot
.\.venv\Scripts\python.exe manage.py run_scheduler
```

В админке откройте «Настройка ежедневной выдачи»: по умолчанию **18:00 по Москве**. Запускайте один планировщик. Он проверяет расписание при старте и каждые 2 секунды, читает изменения времени без перезапуска и не запускает polling. Для получения и обработки ответов нужен одновременно работающий процесс бота.

Остановка: нажмите **Ctrl+C в каждом из трёх терминалов**. Бот освобождает сетевую сессию при выходе, отмене задачи и ошибке. Одновременно запускайте только один polling-процесс с этим токеном. Существующий webhook может вызвать конфликт polling; команда не удаляет его автоматически.

Логи запуска и ошибок идут в консоль. Форматтер скрывает значения токена и ключа, Telegram API URL и токены в traceback. Ошибки настройки Django, токена, сети и внутренней работы различаются. Диагностика команды показывает класс исключения, файлы, строки и функции стека, но не текст исключения, исходные строки кода или локальные переменные.

## Проверки

Автономные проверки, без токена и Telegram API:

```powershell
Set-Location D:\projects\spaced-repetition-bot
.\.venv\Scripts\python.exe manage.py test
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
.\.venv\Scripts\python.exe manage.py migrate --check
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe -m pip check
```

Тесты подменяют настройки в своём процессе и запрещают исходящие сетевые соединения. Проверяются `/start` через Dispatcher с подменённым транспортом, регистрация и обновление профиля, приглашения и их отзыв через админку, атомарный откат, ограничения БД, назначения тем и подмена POST. Конкуренция двух аккаунтов за ссылку, одного ID за разные ссылки, повтор одного события и временная блокировка проверяются реальными операциями отдельной временной файловой SQLite. Async-интеграция использует `TransactionTestCase`, чтобы ORM в отдельном потоке видел сохранённые данные.

Сохранены проверки банка и переноса вложений, входа и защиты `/admin/`, часового пояса, приоритета окружения, скрытия секретов в логах, завершения CLI без токена, закрытия сессии при успехе/ошибке/отмене и режима getMe. Основные тесты работают с SQLite в памяти и временным каталогом файлов. Рабочие `.env`, `db.sqlite3` и `media/` тестами не изменяются.

Необязательная проверка настоящего соединения (требует токен и сеть, не запускает polling):

```powershell
.\.venv\Scripts\python.exe -m bot --check
```

Ручной сценарий:

1. Выполните миграции, создайте superuser, запустите три процесса указанными командами.
2. Войдите в `/admin/` под созданной учётной записью.
3. Укажите `TELEGRAM_BOT_USERNAME` без @ и перезапустите панель. В разделе «Приглашения» создайте приглашение, явно выбрав курс. Откройте сохранённую запись и скопируйте ссылку. Передайте её ученику самостоятельно: автоматической отправки нет.
4. С незарегистрированного аккаунта отправьте `/start` без ссылки: ожидается просьба получить приглашение, новый ученик не появляется. Затем откройте ссылку в личном чате и нажмите «Начать»: ожидается подтверждение регистрации с пояснением, что темы назначает учитель, а занятие начинается через `/review`.
5. В разделе «Ученики» найдите профиль, задайте удобное имя и отметьте пройденные темы. Сохраните, откройте повторно и проверьте флажки. Снимите отметку и сохраните: назначение отключится без удаления. Повторная отметка включает прежнюю запись и обновляет дату включения. Простое сохранение дату не меняет. Можно отмечать тему без активных заданий.
6. Повторите `/start` и открытие той же ссылки: дубликата нет, имя учителя и темы сохранены. После изменения имени/username Telegram повторите команду: Telegram-поля обновятся, в том числе исчезнувший username. Курс и Telegram ID через панель не редактируются.
7. Откройте использованную ссылку со второго незарегистрированного аккаунта: она недоступна, чужие данные не раскрываются. Создайте другое приглашение и откройте его уже зарегистрированным аккаунтом: новый курс не назначается, приглашение остаётся доступным.
8. Для отзыва выберите доступное приглашение в списке и действие «Отозвать выбранные неиспользованные приглашения». Проверьте недоступность ссылки для нового аккаунта. Использованное приглашение повторно доступным не становится.
9. Отправьте `/start` со ссылкой в группе: бот предложит личный чат, регистрации не будет.
10. Нажмите Ctrl+C в терминале бота: ожидаются сообщения об остановке и закрытой сессии, без traceback. Остановите Django в первом терминале и планировщик в третьем.

Успех getMe подтверждает только доступ к API. Он не подтверждает реальную переписку или ручную остановку в PowerShell.

## Структура

`modules/users` хранит `Student`, `Invitation` и `StudentTopic`. Постоянная идентичность ученика — положительный 64-битный Telegram ID; имена берутся из `message.from_user`. Регистрация и назначение тем находятся в `services.py`. Бот инициализирует Django до импорта моделей и вызывает синхронную транзакцию через `sync_to_async(thread_sensitive=True)`; обработчик получает готовый результат без ленивых запросов.

Регистрация начинает транзакцию с записи, чтобы SQLite получила блокировку до чтения состояния. Уникальные ограничения и условное использование приглашения защищают от повторов и конкуренции. При временной блокировке выполняются ограниченные повторы транзакции; polling повторяет незафиксированное событие до успеха; неудачная транзакция откатывается полностью. Из нарушений целостности повторяется только конфликт уникального Telegram ID; остальные ошибки журналируются без текста исключения и передаются вызывающему коду. Токены приглашений и полный `/start` не записываются в прикладные логи. Назначения проверяют принадлежность тем курсу и атомарно создают или сбрасывают прогресс в `modules/repetitions`.

| Пакет | Ответственность |
|---|---|
| `config` | Окружение, Django, маршруты веб-панели, журналирование |
| `bot` | Telegram-обработчики и запуск polling; прикладная логика вызывается из модулей |
| `modules/users` | Ученики, приглашения, Telegram-привязка |
| `modules/materials` | Курс, темы, задания, эталоны, вложения |
| `modules/repetitions` | Прогресс и следующая дата повторения |
| `modules/study_sessions` | Постоянная очередь, текущий вопрос, попытки, настройка и отметки ежедневной выдачи |
| `modules/checking` | Проверка ответов |
| `modules/delivery` | Журнал updates, постоянная очередь исходящих сообщений, повторы и планировщик |
| `tests` | Автономные проверки |

Модули `modules/materials` и `modules/users` содержат модели, админку и миграции; `users` также содержит прикладные операции регистрации и назначения тем. `repetitions` содержит модель прогресса, миграции, чистые календарные правила и прикладной API. `study_sessions` хранит занятия, попытки и обход заданий; `checking` сравнивает текст; `delivery` непосредственно отправляет сообщения и локальные файлы. Фоновые повторы отправки остаются будущей работой. Локально используются три процесса: панель, polling-бот и планировщик. Развёртывание на сервере не входит в этап.

## Обновление существующей установки

Не пересоздавайте окружение, базу или superuser. Зависимости не изменились. Остановите веб-панель, бот и планировщик. Перед миграцией создайте резервную копию SQLite командой из раздела «Подготовка панели», а также сохраните каталог `media/` вместе с ней. Продолжайте только после успешного копирования.

```powershell
Set-Location D:\projects\spaced-repetition-bot
.\.venv\Scripts\python.exe manage.py migrate
```

Затем выполните команды из раздела [«Проверки»](#проверки) и запустите панель:

```powershell
.\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

`manage.py test` выбирает `config.test_settings` до настройки Django: база находится в памяти, вложения — во временном каталоге с автоматической уборкой. Явный эквивалент: `python manage.py test --settings=config.test_settings`. Локальные `db.sqlite3`, `media/` и `.env` тестами не меняются. Исходящая внешняя сеть запрещена; loopback разрешён для Windows asyncio. Все 9 проверок первого этапа включены в общий запуск. Для отдельных старых проверок допустимо `python -m unittest tests.test_foundation`; `unittest discover` не является запуском всего проекта, поскольку не создаёт тестовую БД.

## Работа с банком и ручной сценарий панели

1. Запустите веб-панель и войдите под существующим superuser в `/admin/`.
2. В разделе «Учебные материалы → Курсы» создайте курс: название обязательно, описание необязательно. Автоматически курс не создаётся.
3. Создайте тему, выберите курс, задайте название и неотрицательный порядок. При равном порядке темы и задания сортируются по ID. После первого назначения ученику менять курс темы нельзя, даже если назначение отключено; название, описание и порядок остаются редактируемыми.
4. Создайте задание в теме: короткое название для учителя, порядок, флажок «Активно» выключен. Пустые условие и ответ допустимы для черновика.
5. Попробуйте включить «Активно» без условия или ответа: форма покажет ошибку. Вложение не заменяет текст условия.
6. Заполните условие и ответ `001`, активируйте и сохраните. Откройте снова: ведущие нули сохраняются. Формы удаляют только пробелы по краям; регистр и внутренние пробелы сохраняются.
7. В разделе «Вложения» добавьте картинку или файл. Кнопкой «Добавить ещё одно вложение» добавьте дополнительные строки — по одному файлу в каждой. После сохранения нажмите «Скачать вложение» и сравните содержимое. Перезапустите веб-панель, повторите скачивание.
8. Замените вложение другим файлом, в том числе с таким же именем. Проверьте скачивание нового содержимого. Для удаления вложения отметьте «Удалить» в соответствующей строке и сохраните. Остальные вложения сохранятся.
9. Измените название или условие задания и сохраните. В списке проверьте поиск по названию/условию и фильтры по курсу, теме, активности.
10. Выберите задания и действие «Деактивировать выбранные задания» либо снимите «Активно» в форме. Они исключены из новых попыток `/review`; уже открытый вопрос использует сохранённый снимок.
11. У задания нет кнопки удаления и массового удаления. Курс с темами и тему с заданиями удалить нельзя (PROTECT). Пустые темы и курсы можно удалить штатно.
12. Выйдите из панели и откройте сохранённую ссылку вложения: требуется вход. Сотруднику без права `materials.view_task` скачивание запрещено; superuser имеет это право автоматически.

Этот список — инструкция для ручной проверки, а не утверждение о выполненном браузерном тесте. Автоматические тесты проверяют формы и маршруты через Django test client.

### Хранение и ограничения

Задание может содержать несколько вложений. Каждая запись `TaskAttachment` хранит один файл в `MEDIA_ROOT`; файлы отображаются в порядке добавления. UUID-каталог обеспечивает уникальность хранения даже для одинаковых исходных имён. Файлы сохраняются на диске и доступны после перезапуска. Скачивание выполняется через `/admin/materials/task/<task_id>/attachments/<attachment_id>/`, только для авторизованного активного сотрудника с правом просмотра задания. Клиент передаёт ID задания и вложения, принадлежность вложения заданию проверяется; ответ FileResponse принудительно скачивает файл. Весь `media/` публично не раздаётся. Отсутствующее вложение или файл возвращают 404.

Замена файла меняет ссылку в записи `TaskAttachment`, удаление вложения удаляет эту запись. **Старые файлы автоматически не удаляются**: они остаются в `media/` и занимают место. Резервное копирование должно включать базу и каталог вложений вместе. Обработка изображений, импорт и отдельный статус архива не добавлены. История попыток доступна из карточки ученика.

Правила активации находятся в `Task.clean()`, `Task.save()` вызывает `full_clean()`. Деактивация в админке также проходит модельную проверку. Проверка смены курса темы находится в `Topic.clean()`, а `Topic.save()` также вызывает `full_clean()`. Не используйте `QuerySet.update()`, `bulk_create()` или `bulk_update()` для изменений заданий и тем: эти низкоуровневые операции Django обходят `save()` и модельную валидацию. Массовой активации в интерфейсе нет.


### Обновление до нескольких вложений

Выполните `python manage.py migrate` и перезапустите веб-панель. Миграция `0002` переносит существующие ссылки в таблицу вложений; сами файлы остаются на прежних местах. Новые ссылки скачивания содержат ID задания и ID вложения. Старый адрес одиночного вложения больше не используется.

В форме задания доступны добавление нескольких строк файлов, замена отдельного файла и удаление выбранных вложений. Удаляется запись связи, а файл остаётся на диске согласно прежнему правилу хранения. Право изменения задания позволяет управлять его вложениями; для скачивания необходимо право просмотра задания. Обратная миграция запрещена, если хотя бы у одного задания несколько вложений: их нельзя без потери данных свернуть в одно поле. Для отката используйте согласованную резервную копию базы и файлов.


### Проверки после ревью этапа 3 и известное ограничение

Регрессионные тесты дополнительно проверяют запрет переноса назначенной темы (включая отключённое назначение), загрузку курсов без запроса на каждую тему, конкуренцию отзыва и использования приглашения, различение ошибок регистрации и безопасную диагностику запуска. Обратная миграция вложений проверяется как для одного файла, так и для отказа при нескольких файлах без потери записей.

Пока не устранён конфликт одновременного сохранения формы админки и записи бота в SQLite: панель может вернуть `database is locked` / HTTP 500. После завершения другой записи повторите сохранение. Повторные попытки регистрации не защищают транзакцию панели; исправление отложено отдельно.


## Этап 4: расписание без Telegram

`TopicProgress` связан обязательным `OneToOneField` с `StudentTopic` (удаление назначения защищено `PROTECT`). Хранит только `interval_step` (0–6, ограничение БД) и `next_review_date` (`DateField`). Активность хранится только в назначении. Редактирование прогресса через админку не открыто; назначайте темы существующей формой ученика.

Ступень 0 означает начало или сброс. По умолчанию верные ответы переводят её по цепочке 1 → 2 → 3 → 4 → 5 → 6 → 6 с интервалами 1, 3, 7, 14, 30, 60, 60 дней (согласовано 25.09.2026). Любой неверный ответ даёт ступень 0 и один день; следующий верный — ступень 1 и один день. Новый срок всегда считается от московской даты принятого ответа, включая просроченный ответ.

Настройки находятся в [`config/repetitions.py`](config/repetitions.py):

```python
ERROR_RETRY_DAYS = 1
SUCCESS_INTERVAL_DAYS = (1, 3, 7, 14, 30, 60)
```

Числа — положительные целые календарные дни. Каждый элемент списка задаёт следующую ступень после верного ответа; последний интервал повторяется неограниченно. Число ступеней (`MAX_STEP`) вычисляется автоматически. Для изменения длительности поменяйте значения и перезапустите процессы: миграция не нужна. Уже сохранённые даты не пересчитываются, новые интервалы используются при следующих ответах.

Если добавляете или удаляете ступени, также выполните `python manage.py makemigrations repetitions`, затем после резервного копирования `python manage.py migrate`: меняется ограничение диапазона в БД. Перед сокращением числа ступеней необходимо отдельно перенести прогресс с удаляемых ступеней; автоматического сброса нет. Исторические миграции не редактируйте. Тесты стандартной цепочки фиксируют исходные значения; при намеренном изменении политики обновите ожидаемые даты этих тестов. Демонстрация автоматически использует текущий конфиг.

Публичные операции:

- `modules.users.services.assign_topics(student_id, topic_ids, *, now)` — единственный вход для замены активных назначений. В одной транзакции проверяет курс, сохраняет назначения и прогресс. При первом включении и повторном включении: ступень 0, дата готовности равна московской дате `now`. Повторное включение сохраняет ID назначения и обновляет `activated_at`. Неизменённое сохранение не меняет прогресс и дату включения. Отключение сохраняет прогресс, исключая тему из выдачи кандидатов. Тема без заданий также получает прогресс.
- `modules.repetitions.scheduling.calculate_transition(interval_step, correct, *, now)` — чистый расчёт, возвращает неизменяемый `Schedule(interval_step, next_review_date)`.
- `modules.repetitions.services.apply_result(assignment_id, correct, *, now)` — транзакционно применяет принятый результат к актуальному состоянию БД, возвращает `TopicProgress`. `correct` — строго `True` или `False`; недоступная проверка не является ошибочным ответом. Отключённое назначение отклоняется с `ValueError`, неизвестное — с `StudentTopic.DoesNotExist`.
- `modules.repetitions.services.due_topics(student_id, *, now)` — материализованный список активных `StudentTopic` с датой ≤ московской даты `now`, в порядке `(next_review_date, topic.order, topic_id)`. Связанные `topic` и `progress` загружены. Чтение ничего не записывает, одна просроченная тема возвращается один раз; наличие заданий не фильтруется. Это кандидаты, ещё не сохранённая очередь.

`now` обязателен и должен быть timezone-aware; naive datetime отклоняется до записей. Все календарные расчёты явно используют `Europe/Moscow`, независимо от активного часового пояса Django и ОС. Граница админки и Telegram получает `timezone.now()` и передаёт его сервису. Отсутствие ответа не вызывает перехода. Дата готовности не означает немедленную отправку: её выполняет планировщик этапа 6 в заданное время (по умолчанию 18:00).

Повторный вызов `apply_result` — новый переход. В учебном цикле его вызывает только `accept_answer`: попытка повторно читается и закрывается в общей транзакции с прогрессом и курсором. Повторное завершение того же ID попытки ничего не меняет. Отключение темы отменяет открытую попытку внутри транзакции `assign_topics`. Журнал обработанных Telegram updates реализован в этапе 7.

Запись перед чтением состояния получает блокировку SQLite; конкурентные принятые результаты не затирают ступень из устаревшего объекта. Ошибка блокировки откатывает всю операцию; прикладной слой этапа 7 ограниченно повторяет её. Уже открытая HTTP-транзакция админки может конфликтовать с записью бота: известное ограничение `database is locked` / HTTP 500 остаётся. Не создавайте назначения и не меняйте прогресс напрямую через ORM: при обнаружении отсутствующего прогресса API выбрасывает `InconsistentProgressError`, а не восстанавливает расписание незаметно.

### Миграции и автономная демонстрация

`repetitions.0001_initial` создаёт таблицу; `0002_existing_assignments` переносит все существующие назначения, включая отключённые, в ступень 0 с московской датой исторического `activated_at`. Миграция использует исторические модели и alias соединения, не меняет исходные назначения, банк и вложения. Обычный повторный `migrate` прогресс не сбрасывает. Откат схемы приложения удалит накопленный прогресс: для возврата используйте согласованную резервную копию.

Создание миграций не обновляет рабочую установку. После резервной копии выполните:

```powershell
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py migrate --check
```

При реализации этапа 4 рабочая БД автоматически не мигрировалась; при оценке 25.09.2026 обе миграции этапа 4 уже применены. Перед этапом 6 миграции этапа 5 уже применены. Новая миграция этапа 6 автоматически не применяется. Для автономных проверок запустите команды раздела «Проверки». Проверка пустой временной файловой БД, обновления с этапа 3 и управляемый пример API выполняются отдельно:

```powershell

```

Пример использует временную SQLite и удаляет её после завершения. В начале выводит текущие интервалы из `config/repetitions.py`. Последовательность: включение 21.09.2026 → два верных ответа → ошибка → верный ответ → отключение → повторное включение через два дня. Ответы принимаются в рассчитанные даты повторения; ожидаемые ступени и даты вычисляются из конфига. Отключение сохраняет расписание, повторное включение сбрасывает ступень на 0 и ставит дату готовности в день включения. Редактировать демонстрацию после изменения интервалов не требуется.

Автономные тесты покрывают календарные границы и месяцы обучения, форму админки через test client, откаты, миграцию исторических данных и реальные конкурентные операции на временной файловой SQLite. Это не ручная проверка браузера или переписки Telegram. Ежедневный планировщик описан в разделе этапа 6 ниже.

## Этап 5: ручное занятие

`/review` открывает либо продолжает занятие. Условие передаётся полностью без разметки, длинный текст разбивается на части до 4096 UTF-16 единиц. Затем все вложения отправляются отдельными документами в порядке `TaskAttachment.pk`, включая изображения и файлы с одинаковыми именами. Источник файлов — локальный `MEDIA_ROOT`; ссылки админки и эталон в отправку не попадают.

Обычный текст сравнивается со снимком эталона после `strip()` обеих строк. Регистр, внутренние пробелы, пунктуация, Unicode и числовой формат сохраняют значение: `01` и `1`, `1.0` и `1` различаются. Пустой текст, команды, фото, документы, голосовые, стикеры и подписи к ним не завершают попытку. Учебные операции доступны только зарегистрированному Telegram ID в личном чате.

После ответа бот сообщает «Верно» или «Неверно», затем открывает следующий вопрос. Ошибка завершает попытку без немедленного исправления. Итог показывает принятые, верные, неверные ответы и отдельно пропуски/отмены. Недоступная проверка или техническая ошибка не считаются неверным ответом.

### Состояние, очередь и обход

`StudySession` хранит начало, завершение и пропуски; `Attempt` — исходное назначение, защищённую ссылку задания, состояние, принятый ответ и снимки условия, эталона, названия темы, упорядоченных путей/имён файлов. Эталон отсутствует в транспортном `Question`. Изменение или перенос задания, названия темы и записей вложений не меняет открытую попытку. Старые файлы по прежней политике банка не удаляются автоматически.

На этапе 6 `ReviewQueueItem` сохраняет очередь в базе. Явный `/review` и ежедневная выдача добавляют наступившие темы в порядке `(next_review_date, topic.order, topic_id)` в конец очереди без дубликатов ожидающих/открытых элементов. После ответа выполняется только переход по сохранённой очереди. Уже пропущенная тема не проверяется повторно в текущем ручном обходе; её повторно проверит новый цикл `/review` или следующая ежедневная выдача. Пропуск не меняет расписание. За пропущенные дни отдельные вопросы не накапливаются. В многодневном занятии ранее отвеченная тема может повториться при наступлении следующего срока.

Активные задания выбираются по `(order, pk)`. `TaskCursor` продвигается только после принятого верного или неверного ответа. Если последнее задание ещё активно в этой теме, следующее берётся после него в текущем порядке с возвратом к первому. Добавления и перестановки учитываются при следующем открытии. Если последнее задание отключено или перенесено, берётся первое после сохранённого ключа `(order при открытии, pk)`; если такого нет — первое активное. Это детерминированный обход; при редактировании порядка возможны повторения/пропуски внутри оборота. Единственное задание повторяется в следующих занятиях; ученики и назначения независимы.

Снятие флажка темы в форме ученика атомарно отменяет её ожидающие элементы очереди и открытую попытку, не применяя результат. Поздний ответ отбрасывается, бот объясняет отмену и продолжает оставшиеся темы; он не проверяет этот текст по следующему, ещё не показанному вопросу. `/review` также продолжает после отмены. Повторное включение сбрасывает расписание и удаляет курсор, сохраняя историю; следующий обход начинается с первого задания. Неизменённое сохранение формы ничего не сбрасывает.

Частичные уникальные индексы запрещают два открытых занятия и две открытых попытки ученика. CHECK проверяет согласованность статуса, ответа и времени завершения. SQLite-триггеры проверяют принадлежность попытки ученику занятия/назначения и защищают исторические связи; перенос `Task.topic` разрешён. Эти триггеры относятся к текущему стеку SQLite и потребуют пересмотра при смене СУБД.

### Прикладной API и ограничения доставки

В `modules.study_sessions.services`: `start_review(student_id, *, now)`, `current_question(student_id)` и `accept_answer(student_id, attempt_id, response, *, now, checker=check_exact)`. Возвращаются материализованные DTO без ORM и эталона. Telegram вызывает синхронные сервисы через `sync_to_async(thread_sensitive=True)`; сетевые вызовы выполняются после транзакций. Текст принятого ответа и эталон не записываются в прикладные логи.

Повтор `/review` показывает ту же открытую попытку и вложения даже после перезапуска/полуночи. Пока предыдущая отправка ожидает или повторяется, новый параллельный набор не создаётся. Ошибка сети или отсутствующий файл оставляет вопрос открытым; подтверждённые части сохраняются и не пересылаются. Принятый ответ, продолжение нужной сессии и исходящие сообщения фиксируются одной транзакцией. Подробные гарантии и ограничения этапа 7 описаны ниже. Конфликт конкурентного сохранения формы админки и бота в SQLite (`database is locked` / HTTP 500) остаётся отдельным ограничением панели.

- `study_sessions.0001_initial`: занятия, попытки, курсоры и ограничения состояния/уникальности.
- `study_sessions.0002_relationship_guards`: ограничения принадлежности и исторических связей SQLite.

Автономная демонстрация использует временные БД и файлы, не токен и не рабочие данные:

```powershell
.\.venv\Scripts\python.exe -m tests.review_demo
```

Она проверяет миграцию пустой БД, обновление структуры этапа 4 с фикстурами материалов/ученика/назначения/прогресса/вложений, сохранение дат и ссылок, запись ступени 6 и отклонение 7 непосредственно БД, повторный `migrate` и `migrate --check`. Затем показывает полное занятие из двух тем, четыре файла, повтор `/review`, верный/неверный ответ и итог. SQLite-соединения закрываются до удаления временного каталога. Полный `manage.py test` дополнительно проверяет обработчики через подменённый транспорт и сбои доставки. Успех этих проверок не подтверждает реальную доставку Telegram.

Ручной сценарий реального Telegram (выполняется отдельно):

1. После резервной копии и миграций запустите два процесса. Создайте две темы курса, несколько активных заданий с разным порядком и эталонами, добавьте к одному заданию два файла с одинаковым исходным именем.
2. Зарегистрируйте ученика приглашением и назначьте обе темы через форму ученика.
3. В личном чате вызовите `/review`: проверьте полное условие и все файлы. Повторите `/review`: должен прийти тот же вопрос без смены задания.
4. Ответьте верно на первый вопрос, неверно на второй. Проверьте порядок «результат → следующий вопрос», отсутствие эталонов и итог: два ответа, один верный, один неверный.
5. Для отдельной проверки отмены снимите и снова поставьте флажки тем, начните новое занятие. Пока вопрос открыт, отключите его тему в админке; отправьте поздний ответ. Ожидаются объяснение отмены и другой вопрос без зачёта позднего текста. После повторного включения и нового занятия обход начинается с первого задания.
6. Проверьте `/unknown`, фото с подписью, пустой текст и ввод в группе: попытка и прогресс не должны изменяться.

Этот ручной сценарий не выполнялся автоматически. Планировщик реализован на этапе 6; надёжность и персональная статистика добавлены в этапе 7, их ручная приёмка описана ниже.

## Этап 6: ежедневная выдача и постоянная очередь

Настройка «Ежедневная выдача» находится в Django Admin в разделе учебных сессий. В базе существует одна запись с московским временем; её нельзя удалить или добавить вторую. Значение по умолчанию — **18:00**. Планировщик читает его при каждом проходе. Если время перенесли раньше и оно уже наступило, ещё не обработанные сегодня ученики получат выдачу на ближайшем проходе. Для уже обработанных учеников новая выдача будет только в следующий день.

Очередь формируется один раз в сутки для каждого ученика, включая дни без подходящих заданий. Открытый вопрос сохраняется, новые темы добавляются в конец очереди; напоминания и повторные отправки открытого вопроса не выполняются. Тема, включённая после сегодняшней выдачи, автоматически появится в следующей. Явный `/review` добавляет наступившие темы сразу, даже до установленного времени. Ответ продолжает уже сохранённую очередь, не формируя новый набор тем. Продолжение привязано к сессии принятого ответа: если планировщик завершил её во время отправки результата, обработчик возвращает её накопленный итог без создания пустого занятия.

После простоя до времени сегодняшней выдачи планировщик ждёт этого времени; после него — сразу собирает просроченные темы. На каждую тему приходится не более одного ожидающего/открытого элемента, независимо от числа пропущенных дней. Перезапуск не сбрасывает очередь и отметки выдачи. Если вопросов нет, автоматических сообщений не будет. Темы без активных заданий пропускаются без изменения прогресса; следующая ежедневная выдача проверит их снова.

Пока компьютер выключен, выдача и приём ответов недоступны. Нужны **три процесса**, описанные выше. Без polling-бота планировщик может отправить вопрос, но ответы будут обработаны только после запуска бота. Команда `run_scheduler --once` делает один проход **с реальной отправкой**, это не автономный тест.

### Состояние и API

- `DailySchedule`: единственное общее время выдачи.
- `DailyReviewRun`: уникальная пара «ученик — московская дата»; создаётся атомарно вместе с очередью. Ошибка формирования откатывает и отметку, и элементы, позволяя повторить проход.
- `ReviewQueueItem`: назначение темы, занятие, время постановки, состояние и ссылка на попытку после открытия. Состояния: ожидает, открыто, завершено, пропущено, отменено. Снимок задания создаётся при открытии, поэтому ожидающие темы используют актуальный банк.
- `start_review(student_id, *, now)`: ручное пополнение очереди и показ текущего вопроса.
- `continue_review(student_id, *, now, session_id=None)`: продолжение конкретной сессии после ответа по `session_id` из результата `accept_answer`; завершённая сессия возвращает исторический итог. Без ID продолжает только существующую открытую очередь (для поздней отмены), новое занятие не создаёт.
- `form_daily_review(student_id, *, now)`: идемпотентное формирование ежедневной выдачи; при открытом вопросе возвращает `idle`, чтобы не отправлять его повторно.
- `modules.delivery.scheduler.run_tick(bot, *, now)`: один проход с независимой обработкой учеников и отправкой после транзакций.

Ступени и интервалы повторения не изменены. В длинном занятии одна тема может встречаться несколько раз, когда снова наступил её срок. Уникальность теперь относится к живому элементу очереди и связанной с ним попытке, а не к паре «сессия — тема». Сохраняются ограничения одного открытого занятия и одного открытого задания ученика.

Ошибка отправки одному ученику сохраняет отметку выдачи и открытую попытку. В этапе 7 исходящие части фиксируются атомарно с выдачей и восстанавливаются независимо от ежедневной отметки; временные ошибки повторяются автоматически. После окончательной ошибки устраните причину и используйте `/start`; `/review` также восстанавливает доставку и дополнительно запускает или продолжает занятие зарегистрированного ученика. Неопределённый результат Telegram может привести к повтору одной части той же попытки, без нового учебного перехода.

Ручная приёмка выполняется отдельно:

1. На тестовом ученике назначьте две темы с активными заданиями, включая задание с несколькими вложениями. Установите время выдачи на ближайшую минуту и запустите все три процесса.

## Надёжность и персональная статистика — этап 7

`modules/delivery/application.py` объединяет учебные сервисы: журнал входящего события, принятый ответ, прогресс, курсор, продолжение именно его сессии и outbox сохраняются одной транзакцией. Ежедневная отметка и исходящий вопрос также фиксируются вместе. Сеть вызывается после commit; её сбой не теряет следующий вопрос или итог. В журнале — числовой ID бота и `update_id`, статус, время и связи; токен, приглашение и полный Telegram JSON не сохраняются. Все ответы `/start`, `/review`, результаты, итоги, сообщения о неподдерживаемом формате и отказах тоже проходят через outbox. Дубль обработанного update не создаёт новые записи и не обновляет профиль или прогресс повторно.

### Приём сообщений и границы восстановления

В установленном aiogram 3.31.0 `_listen_updates` продвигает offset после `yield update`, а `_process_update` по умолчанию поглощает исключение. Поэтому используется `ReliableDispatcher` с `handle_as_tasks=False`: он повторяет неуспешную операцию через 5 секунд, не возвращаясь к генератору до успешной фиксации. SQLite-операции целиком повторяются до 4 раз с паузами 0,05 / 0,10 / 0,15 секунды; незавершённая транзакция полностью откатывается. Состояние «processing» не остаётся после аварии, поскольку журнал и обработка находятся внутри одной транзакции. Сбой после commit восстанавливает outbox, повтор update становится пустой учебной операцией.

Polling должен работать в одном экземпляре. Это не постоянный inbox: необработанные события до commit остаются у Telegram. Telegram хранит updates ограниченное время (до 24 часов); длительный простой, другой получатель updates с тем же токеном или ручное подтверждение offset могут привести к потере входящего сообщения. Постоянная ошибка обработки задерживает последующие updates: смотрите безопасную диагностику и исправляйте причину. Неверный токен при отправке завершает процесс с ошибкой конфигурации; учебный прогресс не изменяется от транспортной ошибки.

Ответ проверяется по конкретной попытке. Новый вопрос допускает ответ только после подтверждения **всех** частей условия и вложений. Для обычного текста его Telegram message ID должен быть больше ID последней части вопроса: текст, отправленный до выдачи нового задания и обработанный позднее, не закроет его. Для явного reply используется сохранённый ID сообщения вопроса; старый, чужой или неизвестный вопрос не переносится на текущую попытку. Ответ на частично отправленный вопрос не принимается. Для вопросов этапа 6 без достоверной доставки разрешён обычный ответ; `/review` создаёт подтверждаемую отправку.

Message ID не доказывает намерение ученика. Запоздалый обычный текст, отправленный уже после нового вопроса, может быть неотличим от ответа на него и трактуется как ответ на текущий доставленный вопрос. Рекомендуйте Telegram reply для однозначной привязки. Одинаковые тексты разных допустимых ответов не считаются дублями.

### Очередь отправки и ошибки

Одна outbox-запись соответствует одной части текста или одному файлу. Условие разбивается без потери символов с учётом UTF-16; файлы отправляются в порядке снимка, эталон в payload отсутствует. Порядок одной переписки: результат → следующий вопрос с файлами либо результат → итог. Итог хранит результат нужной сессии даже после начала другой. Ошибка в одном чате не мешает обработке других; неисправный чат ждёт восстановления своей первой неуспешной части.

Оба процесса — бот после события и планировщик — используют один захват outbox. Он выполняет условную запись в SQLite с UUID владельца и сроком 60 секунд; сеть ограничена 20 секундами (HTTP-сессия — 15 секунд). Просроченный захват освобождается на следующем проходе; старый владелец не может записать успех за нового. Транзакции не содержат сетевых вызовов и не полагаются на `select_for_update` для SQLite.

Планировщик делает проход сразу и затем через 2 секунды после завершения предыдущего; за проход обрабатывается до 100 частей. Время ежедневной выдачи остаётся отдельной настройкой, по умолчанию 18:00 Москвы. Доставка обрабатывается также до этого времени и в дни без новых заданий. Если планировщик выключен, бот может отправить ожидающие части в чате текущего события; фоновые повторы и автоматическая выдача ждут планировщика.

| Ошибка | Поведение |
|---|---|
| Сеть, timeout, временная ошибка Telegram | До 10 попыток; задержки 5, 10, 20, 40, 80, 160, 320, 640, 900 секунд; затем окончательная ошибка |
| Ограничение частоты | Повтор не раньше указанного Telegram `retry_after`, без сна обработчика; общий предел 10 попыток |
| Блокировка, недоступный чат | Окончательная ошибка; после разблокировки пользователь отправляет `/start` или `/review` |
| Пропавшее/недопустимое вложение или отказ Telegram принять файл | Окончательная ошибка; восстановить файл снимка или исправить причину, затем `/start` или `/review` |
| Неверный токен | Безопасная категория `configuration`, остановка процесса; исправить локальную конфигурацию и перезапустить, затем `/start` или `/review` |
| Другая ошибка транспорта | Окончательная ошибка для диагностики, без бесконечного повтора |

Явный `/start` в личном чате от допустимого пользователя возобновляет части с окончательной ошибкой в текущей переписке, в том числе до регистрации и без приглашения. Восстановление выполняется после проверки дедупликации в одной транзакции с регистрацией, журналом события и новыми исходящими сообщениями. Оно сохраняет порядок очереди, сбрасывает счётчик повторов неудавшихся частей, не пересылает подтверждённые части и не восстанавливает отменённые вопросы. Повтор того же `update_id` не сбрасывает повторы и не добавляет сообщения. `/start` не открывает учебную попытку и не меняет прогресс. `/review` зарегистрированного ученика также восстанавливает доставку (включая сохранённые результаты/итоги) и дополнительно запускает или продолжает занятие. Для уже полностью доставленного открытого вопроса новый `/review` создаёт повторный показ той же попытки; до завершения этого показа ответы не принимаются. Неудавшаяся доставка не служит новым ежедневным заданием или напоминанием.

После ответа или отключения темы оставшиеся части вопроса отменяются. Уже отправляемая по сети часть может прийти поздно; она не открывает попытку заново и не позволяет зачесть её после отмены. Exactly-once доставка не обещается: если Telegram принял часть, а процесс упал до сохранения успеха, после окончания захвата возможен повтор этой части той же попытки. Учебный результат от этого не дублируется. При неизвестном ID такой первой копии используйте `/review` для повторного показа и явный reply на подтверждённое сообщение.

### Статистика учителя

В карточке ученика откройте «Прогресс, история и доставка». Страница показывает активные и отключённые назначения, ступень и интервал, следующую дату, снимки истории, фильтры по исходной теме, статусу и **московской дате открытия**. Верные, неверные, открытые и отменённые попытки подсчитываются отдельно по текущему фильтру. Перенос задания и переименование темы не меняют исходную связь и снимки. Ступень 0 — первый повтор/повтор после ошибки на следующий день; ступень 6 повторяет через 60 дней. Дата отключённой темы не означает действующую выдачу.

История и отправки имеют пагинацию по 25 записей. Условие, эталон и принятый ответ открываются на отдельной странице попытки, файлы — через защищённый маршрут Admin. Публичного media-маршрута нет. Просмотр требует права на ученика, попытку, прогресс и исходящие сообщения (superuser уже имеет их). Все выборки ограничены учеником из маршрута. Изменение, удаление и POST истории запрещены; назначения редактируются прежней формой. Безопасные категории ошибок и сроки повторов видны здесь же. Действия учителя при окончательной ошибке: устранить причину, попросить пользователя отправить `/start` (либо `/review` для начала или продолжения занятия), проверить доставку и неизменность попытки/прогресса.

ID, снимки, ответы, очередь, прогресс и ежедневные отметки не меняются. Старые открытые попытки имеют неизвестную доставку (нет строки QuestionDelivery): обычный ответ допускается, `/review` показывает снимок через outbox. 1. Остановите панель, polling и планировщик через Ctrl+C.
2. Сделайте согласованную резервную копию SQLite и `media/` командами из [ручной инструкции этапа 7](docs/stage-7-manual-check.md#обновление-рабочей-установки).
3. Выполните `migrate`, `migrate --check` и `check`, затем перезапустите три процесса.

Повторный migrate не сбрасывает прогресс. Обратная миграция с журналом или доставками запрещена: их удаление теряет защиту от повторов и состояние доставки. Откат требует согласованной резервной копии и подходящей версии кода; нельзя объединять старую БД с новыми транспортными журналами. Не создавайте повторно superuser и не меняйте `.env` ради обновления.

Автономные проверки этапа 7:

```powershell
.\.venv\Scripts\python.exe manage.py test
.\.venv\Scripts\python.exe manage.py check --settings=config.test_settings
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run --settings=config.test_settings
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m tests.reliability_demo
```

Демонстрация применяет миграции на временных файловых базах с нуля и с этапа 6, проверяет сохранность истории/триггеров, гонки отдельных соединений, ограниченный повтор SQLite и новый процесс после перезапуска. Реальная Telegram-доставка и ручная приёмка проверяются отдельно по [docs/stage-7-manual-check.md](docs/stage-7-manual-check.md).
