# Серверная сборка: первый запуск, обновление и восстановление

Подготовка этапа 8, 6 октября 2026 года. Это инструкция для сборки из репозитория; приложение Amvera ещё не создано. Результаты автономных проверок и оставшиеся проверки перечислены в [отчёте](stage-8-project-assessment.md).

## Состав

Python 3.14.6 (Docker-образ закреплён также digest), Django 5.2.17, Gunicorn 26.2.0, WhiteNoise 6.12.0. `requirements.txt` закрепляет весь набор пакетов. Контейнер запускает `python -m deploy.supervisor`; локальный `run_dev.py` для сервера не используется. Один Gunicorn worker, один polling-процесс, один планировщик с интервалом 2 секунды. Отказ любого компонента завершает всю группу с кодом 1; платформа должна перезапустить контейнер. SIGTERM/SIGINT завершают группу, после 25 секунд оставшиеся процессы получают SIGKILL. Статика собирается в образ, миграции — только при запуске.

`amvera.yml` задаёт 8080 и `/data` согласно [документации Docker Amvera](https://docs.amvera.ru/applications/configuration/docker.html). Необходимо выбрать один экземпляр и контролируемое обновление с остановкой старого контейнера. Файловая блокировка `/data/.runtime.lock` дополнительно запрещает второй supervisor на том же хранилище. Она не защищает от другого локального polling или второго приложения с другим хранилищем и тем же токеном. До этапа 9 проверить стратегию обновления и поддержку блокировок на реальном хранилище Amvera.

## Окружение

Задавать настройки в кабинете Amvera. Контейнер игнорирует локальный `.env`, а `.dockerignore` исключает секреты, базы, архивы, media и окружения из образа. На сервер не переносить текущие локальные данные.

| Переменная | Значение |
| --- | --- |
| `DJANGO_SETTINGS_MODULE` | `config.production` (уже задано в образе) |
| `DJANGO_DEBUG` | `false` (уже задано в образе) |
| `DJANGO_SECRET_KEY` | Новый случайный секрет длиной не менее 50 символов, вне Git и чата |
| `DJANGO_ALLOWED_HOSTS` | Конкретный домен панели, без схемы; несколько — через запятую, без wildcard |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | `https://` и тот же домен, несколько — через запятую |
| `DJANGO_TRUST_PROXY_HTTPS` | По умолчанию `false`; включить `true` после проверки ingress |
| `DJANGO_DB_PATH` | `/data/db.sqlite3` (по умолчанию) |
| `DJANGO_MEDIA_ROOT` | `/data/media` (по умолчанию) |
| `APP_MODE` | `setup` для первоначального заполнения; `run` для учебной работы |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` | Секрет и имя отдельного тестового/рабочего бота; нужны при `run` |
| `BACKUP_DIR` | `/data/backups` (по умолчанию) |
| `BACKUP_KEEP` | `7` локальных архивов (по умолчанию) |
| `BACKUP_EXPORT_COMMAND` | JSON-массив argv внешнего экспортёра; последний аргумент добавляется автоматически — путь архива |
| `APP_REVISION` | Идентификатор релиза/commit для manifest резервной копии |

Secure cookies, HTTPS redirect, HSTS и CSRF включены серверной конфигурацией. Настройки сверены с [deployment checklist Django](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/). До открытия панели проверить, что Amvera **заменяет**, а не просто пропускает клиентский `X-Forwarded-Proto`, и что запрос к HTTPS-домену не попадает в цикл 301/302. После подтверждения включить `DJANGO_TRUST_PROXY_HTTPS=true`. Автономная проверка с доверенным заголовком не доказывает свойства ingress Amvera. HSTS распространяется на поддомены: использовать выделенный домен, все его поддомены должны поддерживать HTTPS.

## Первоначальная настройка

1. Собрать образ; выбрать постоянное `/data`, один экземпляр, HTTPS-домен и окружение. Оставить `APP_MODE=setup`. На пустом хранилище supervisor применит миграции и `check --deploy --fail-level WARNING`, затем запустит только панель. Ошибка проверки или миграций запрещает запуск компонентов.
2. В терминале **этого контейнера**, с его серверным окружением, выполнить `python manage.py createsuperuser`. Ввести учителя и пароль интерактивно; Django проверит пароль. Пароль не задавать через аргументы, Git, чат или постоянную переменную окружения. Повторно эту команду для того же имени не выполнять.

   Если терминал недоступен при развёртывании через MCP, разрешена одноразовая инициализация в `setup`: перед первым запуском задать секрет `DJANGO_SUPERUSER_PASSWORD`, обычные переменные `DJANGO_SUPERUSER_USERNAME` (по умолчанию `admin`) и `DJANGO_SUPERUSER_EMAIL` (необязательно). Supervisor забирает пароль из своего окружения до запуска дочерних процессов, после миграций проверяет его валидаторами Django и создаёт первого учителя. Если суперпользователь уже существует, его пароль и права не меняются. После сообщения «Первый учитель создан» удалить эти три переменные из Amvera; не сохранять пароль в постоянном окружении проекта. В `run` эта процедура не выполняется.
3. Войти в `/admin/`, заполнить курс, темы, активные задания с эталонами и вложениями. Вложения доступны через защищённые маршруты админки, публичного `/media/` нет. До появления учителя readiness возвращает 503, liveness остаётся 200; это позволяет создать пользователя через терминал до открытия маршрута панели.
4. Настроить внешний экспорт архивов и проверить восстановление на отдельном пустом хранилище. Локальный архив в `/data` не заменяет внешнюю копию.
5. Пройти ручную приёмку этапа 9 на отдельном тестовом боте. Перед рабочим polling остановить все процессы с тем же токеном, проверить `getMe` и отсутствие webhook. Накопленные Telegram updates автоматически не удаляются.
6. Остановить контейнер, переключить `APP_MODE=run`, запустить. Сначала выполняется резервирование существующих данных, миграции и проверки, затем резервирование новой схемы, затем все три компонента. Без учителя, токена или настроенного успешного внешнего экспорта рабочий режим не запустится.

При повторном запуске `setup` существующие данные резервируются перед миграциями; внешний экспорт выполняется, если настроен. Без экспортёра сохраняется локальный архив. Записи панели в `setup` не получают ежедневных копий: этот режим предназначен для короткой первоначальной настройки.

## Резервирование

При рабочем запуске и каждые 24 часа supervisor останавливает **все три компонента**, включая панель и загрузку файлов. Создаёт SQLite snapshot через Backup API, проверяет `PRAGMA integrity_check`, копирует media, добавляет SHA-256 каждого файла и `APP_REVISION`, атомарно публикует `tar.gz`. Затем экспортирует его за пределы приложения и только после успешного экспорта возобновляет работу. Архивы имеют права 0600; ротация удаляет старые локальные копии только после успеха экспорта. Ошибка экспорта оставляет архив и завершает контейнер с ошибкой; успешный старт повторит экспорт новой копии. Перезапуск делает новую копию и отсчитывает следующие 24 часа заново.

Пауза может включать до 25 секунд остановки и время снимка/загрузки. Внешняя команда должна завершиться за 20 секунд; для малой первой группы проверить размер архива и скорость канала. Нельзя размещать резервный каталог внутри media. На внешнем хранилище отдельно настроить срок хранения и доступ только учителю/оператору.

В образе есть пример экспортёра HTTPS PUT:

```text
BACKUP_EXPORT_COMMAND=["python","-m","deploy.export_backup"]
BACKUP_EXPORT_URL=https://ваше-внешнее-хранилище/закрытая-коллекция
BACKUP_EXPORT_TOKEN=секрет-доступа
```

URL — HTTPS-коллекция без query/fragment; к ней добавляется имя архива. Сервис должен принимать PUT с Bearer token и возвращать 200/201/204 **после сохранения**; это не универсальный клиент S3. URL и токен вводить как секреты. Можно поставить собственный экспортёр в образ и указать его argv, без shell; учётные данные — только через окружение. Простая команда, завершающаяся с 0 без сохранения вне приложения, не обеспечивает резервирования. Внешний сервис и его политика хранения выбираются при запуске.

Ручная копия: сначала остановить контейнер и убедиться, что панель/polling/планировщик завершились; затем запустить тот же образ с тем же `/data` в одноразовом режиме `python -m deploy.supervisor backup`. Блокировка не позволяет делать это одновременно с рабочим supervisor. Не копировать открытый SQLite-файл обычным `cp` и не запускать сторонние записи вне supervisor во время снимка.

## Обновление и откат

1. Остановить старый контейнер; дождаться завершения всех процессов. Заблокировать входящие изменения панели на время обновления.
2. Одноразово выполнить `backup` старым образом. Сохранить старый digest образа и проверить внешнюю копию. Это копия для согласованного отката версии и данных.
3. Собрать новый образ, запустить его на том же `/data`. Supervisor также резервирует базу **до миграций**. Миграции не выполняются на этапе сборки, не запускаются параллельно с ботом или панелью.
4. Проверить readiness, вход, CSS/JS, продолжение сохранённого занятия и отсутствие второго polling. Только после этого вернуть обычный доступ.
5. Для отката остановить новый контейнер. Если старая версия совместима со схемой, запустить старый образ. Иначе выделить пустое хранилище, восстановить архив, сделанный старым образом, и использовать именно старый образ. Не пробовать lossy reverse миграций поверх рабочей истории. Изменения после времени архивирования будут потеряны — зафиксировать границу потери перед откатом.

Восстановление на пустое хранилище, при остановленных процессах:

```bash
python -m deploy.supervisor restore --archive /путь/к/архиву.tar.gz
```

Команда требует отсутствующую базу и пустое media, проверяет SHA-256 и SQLite integrity. Она не запускает миграции или Telegram. После восстановления на отдельной установке оставить `APP_MODE=setup`: рабочий polling нельзя запускать параллельно оригиналу. Сверить историю, открытое занятие, очередь, прогресс и файлы; затем переходить к рабочему режиму только после остановки оригинала. Исходное рабочее хранилище сохранять до подтверждения восстановления.

## Контроль состояния

`/health/live/` показывает активность supervisor (не старше 15 секунд). `/health/ready/` проверяет базу, учителя, активность supervisor и в `run` дополнительно:

- успешный проход планировщика и успешное получение Telegram updates не старше 120 секунд;
- ошибки отдельного ученика в планировщике или входящего события дольше 5 минут; ученик с ошибкой выдачи повторяется раз в минуту, а не на каждом проходе;
- входящее событие, отклонённое за последние 24 часа (`incoming_failed`): после примерно минуты неудачных повторов бот отмечает событие как отклонённое, сообщает ученику, что сообщение не засчитано, и продолжает обработку остальных чатов;
- больше 100 ожидающих частей outbox или часть старше 15 минут; возраст учитывает `created_at`, перенос `next_attempt_at` его не обнуляет;
- окончательные ошибки доставки и успешную резервную копию не старше 25 часов.

Здоровый ответ — 200, обнаруженные проблемы — 503 с названиями проверок без персональных данных. Supervisor каждую минуту пишет проблемы готовности в безопасный лог; остальные компоненты пишут stdout/stderr. Внешнему мониторингу отслеживать readiness и логи, уведомлять оператора при 503. Для Kubernetes настроить liveness на `/health/live/`, readiness на `/health/ready/`, startup с достаточным временем для миграций и копирования. HTTP Host пробы должен совпадать с `DJANGO_ALLOWED_HOSTS`. Не использовать readiness для бесконечного рестарта контейнера при временном сбое Telegram; liveness контролирует управляющий процесс. `/health/*` исключены из HTTPS redirect для внутренней пробы. Нужен допуск на короткую паузу ежедневного резервирования.

Старые pending сообщения при миграции получают время внедрения `created_at`; точный возраст до этапа 8 неизвестен. `outbox_failed` требует диагностики причины (например, ученик заблокировал бота); само наличие 503 не исправляет доставку. Постоянный backlog и ошибки не скрываются открытым портом панели.

## Автономные проверки и Docker

На отдельном окружении с Python 3.14.6 и зависимостями:

```bash
DJANGO_SETTINGS_MODULE=config.test_settings python manage.py test
DJANGO_SETTINGS_MODULE=config.test_settings python manage.py makemigrations --check --dry-run
DJANGO_SETTINGS_MODULE=config.build python manage.py collectstatic --noinput
python -m deploy.smoke
```

`deploy.smoke` использует временные данные в `/tmp`, фиктивного учителя и домен `school.example.org`; Telegram не запускает. Нужен свободный порт 8080 и собранная статика. Проверяет Gunicorn, CSS/JS, готовность, единственность владельца хранилища, конкурентные изменения админки/ответа/выдачи, повторный запуск и сохранность базы/media. Unit-тесты дополнительно проверяют остановку зависших потомков, ежедневную паузу и экспорт/восстановление архива.

Проверка образа выполнена на системном Docker Engine 29.8.2 в Ubuntu WSL. Для повторения всего сценария, включая пересоздание контейнера и восстановление в отдельный том:

```bash
sudo systemctl start docker
sudo bash deploy/check_docker.sh
```

Сценарий использует только собственные временные контейнеры и тома, удаляет их после проверки и оставляет образ `spaced-repetition:stage8`. Настоящий off-site экспорт в нём моделируется отдельным тестовым Docker volume. Отдельные команды проверки образа:

```bash
sudo docker build -t spaced-repetition:stage8 .
sudo docker run --rm --entrypoint python spaced-repetition:stage8 -m pip check
sudo docker run --rm --entrypoint python spaced-repetition:stage8 manage.py test --settings=config.test_settings
sudo docker run --rm --entrypoint python spaced-repetition:stage8 -m deploy.smoke
```

Последняя команда проверяет сервер и хранилище в рамках изолированного контейнера. Пересоздание контейнера на **одном и том же Docker volume** в `setup` и восстановление копии в отдельный том выполнены в `deploy/check_docker.sh`: сохранились история, открытое занятие, очередь, прогресс, outbox, учитель и media. Далее проверить три реальных компонента с отдельным тестовым ботом. Проверки ingress, реального Telegram, 24-часового расписания, внешнего хранилища и обновления Amvera относятся к следующим этапам.


## Локальный Docker Engine в Ubuntu WSL

Docker Engine установлен через [официальный apt-репозиторий Docker](https://docs.docker.com/engine/install/ubuntu/), системно для всех проектов этой Ubuntu WSL. Автозапуск `docker.service`, `docker.socket` и `containerd.service` отключён, пользователь не добавлен в группу docker. Сейчас Docker запущен вручную. После остановки или перезапуска WSL запускать явно:

```bash
sudo systemctl start docker
sudo docker version
```

Команды Docker выполнять с административными правами, например `sudo docker build …`. Для ручной остановки Docker и его backend:

```bash
sudo systemctl stop docker.service docker.socket containerd.service
```

Docker Desktop для этой установки не используется. Установка и служба находятся в Ubuntu WSL; они не входят в репозиторий или образ приложения.
