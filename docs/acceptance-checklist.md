# Ручная приёмка учебного цикла

Чек-лист для проверки с настоящим Telegram. Автономные тесты не подтверждают реальную доставку, работу polling и смену календарных суток, поэтому перед работой с учениками нужна ручная приёмка.

Проводите её на отдельной базе, отдельном каталоге вложений и **отдельном тестовом боте**. Рабочие `.env`, базу, `media/` и системные часы не изменяйте. Для одного токена одновременно должен работать только один polling-процесс и один планировщик.

## Изолированная установка

Переменные окружения процесса имеют приоритет над `.env`, поэтому достаточно указать временные пути и токен тестового бота.

**Linux / WSL:**

```bash
export ACCEPTANCE_ROOT="$(mktemp -d /tmp/acceptance-XXXXXX)"
export DJANGO_DB_PATH="$ACCEPTANCE_ROOT/db.sqlite3" DJANGO_MEDIA_ROOT="$ACCEPTANCE_ROOT/media"
export TELEGRAM_BOT_USERNAME=ИмяТестовогоБота
read -rsp 'Токен тестового бота: ' TELEGRAM_BOT_TOKEN && export TELEGRAM_BOT_TOKEN
.venv-wsl/bin/python manage.py shell -c "from django.conf import settings; print(settings.DATABASES['default']['NAME']); print(settings.MEDIA_ROOT)"
```

**Windows / PowerShell:**

```powershell
$env:ACCEPTANCE_ROOT = Join-Path $env:TEMP ('acceptance-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
New-Item -ItemType Directory $env:ACCEPTANCE_ROOT | Out-Null
$env:DJANGO_DB_PATH = Join-Path $env:ACCEPTANCE_ROOT 'db.sqlite3'
$env:DJANGO_MEDIA_ROOT = Join-Path $env:ACCEPTANCE_ROOT 'media'
$env:TELEGRAM_BOT_USERNAME = 'ИмяТестовогоБота'
$credential = [System.Management.Automation.PSCredential]::new('bot', (Read-Host 'Токен тестового бота' -AsSecureString))
$env:TELEGRAM_BOT_TOKEN = $credential.GetNetworkCredential().Password
Remove-Variable credential
.\.venv\Scripts\python.exe manage.py shell -c "from django.conf import settings; print(settings.DATABASES['default']['NAME']); print(settings.MEDIA_ROOT)"
```

Убедитесь, что оба пути находятся во временном каталоге. Далее команды приведены для WSL; в Windows замените `.venv-wsl/bin/python` на `.\.venv\Scripts\python.exe`.

```bash
.venv-wsl/bin/python manage.py migrate
.venv-wsl/bin/python manage.py createsuperuser
.venv-wsl/bin/python run_dev.py --port 8001
```

`run_dev.py` запускает панель, бот и планировщик. Для сценариев, где планировщик должен быть остановлен, запускайте компоненты по отдельности в терминалах с теми же переменными: `manage.py runserver 127.0.0.1:8001`, `-m bot`, `manage.py run_scheduler`. Один проход планировщика — `manage.py run_scheduler --once`. Эти команды отправляют настоящие сообщения.

## Наблюдение за состоянием

Прогресс, история попыток, текущий вопрос и ошибки доставки видны в карточке ученика: ссылка «Прогресс, история и доставка». Очередь занятия и отметки ежедневной выдачи в панели не отображаются. Для них есть команда, которая только читает данные; подставьте Telegram ID ученика:

```bash
.venv-wsl/bin/python manage.py shell -v0 -c "from modules.users.models import Student; from modules.study_sessions.models import StudySession, ReviewQueueItem, DailyReviewRun; s = Student.objects.get(telegram_id=123456789); print('Сессии:', list(StudySession.objects.filter(student=s).values_list('id', 'state'))); print('Очередь:', list(ReviewQueueItem.objects.filter(session__student=s).values_list('session_id', 'assignment__topic__title', 'state', 'attempt_id'))); print('Выдачи:', list(DailyReviewRun.objects.filter(student=s).values_list('local_date', flat=True)))"
```

В любой момент у ученика не более одной открытой сессии и одной открытой попытки, а у темы — не более одного элемента очереди в состоянии `pending` или `open`.

## Тестовые данные

Создайте курс и темы:

| Тема | Задания (условие → эталон) |
| --- | --- |
| A | A1 → `11`, A2 → `12`. К A1 добавьте длинное условие (больше 4096 символов) и два небольших файла |
| B | B1 → `22` |
| Пустая | Без активных заданий |
| Отмена | O1 → `33` |
| Последняя | L1 → `44` |

Зарегистрируйте два тестовых аккаунта по разным приглашениям и назначьте им темы в карточках. Данные второго ученика должны отличаться, чтобы проверить, что история не смешивается.

## Сценарии

### Регистрация и ручное занятие

1. `/start` без приглашения не регистрирует нового пользователя. Приглашение регистрирует один раз; повторный `/start` обновляет только Telegram-профиль и не создаёт дубликат. Использование в группе и аккаунтом бота не расходует приглашение.
2. `/review` показывает тему, условие A1 целиком и оба файла в сохранённом порядке, без эталона. Повторный `/review` показывает ту же попытку, новая не создаётся. Пока повторный показ не доставлен полностью, ответ не принимается.
3. Ответ `11` обычным текстом: «Верно.» приходит до B1. Неверный ответ на B1: эталон не раскрывается, ступень B становится 0, следующая дата — завтра по Москве. Пробелы по краям ответа удаляются, а регистр, внутренние пробелы и формат числа сохраняются.
4. При открытом вопросе отправьте неизвестную команду, файл с подписью, голосовое и пустое сообщение. Бот объясняет формат, попытка остаётся открытой, прогресс не меняется. Измените условие и эталон открытого задания или деактивируйте его в банке: открытая попытка показывает и проверяет исходный снимок.
5. Отправьте два ответа быстро, до прихода следующего вопроса: закрывается только первое задание. Telegram reply на предыдущее задание после нового вопроса не засчитывается новому. Обычный текст, отправленный уже после нового вопроса, считается ответом на него; для однозначной привязки используется reply.
6. Отмена и итог. Назначьте A, B, «Пустая», «Отмена», «Последняя» при остановленном планировщике. Через `/review` ответьте A1 верно и B1 неверно; бот сообщает о пропуске «Пустой» и открывает O1. Отключите «Отмена» в карточке и ответьте на O1: ответ не засчитывается, бот сообщает об отмене и открывает L1. После верного L1 итог: `Ответов: 3; верных: 2; неверных: 1. Пропущено тем: 1; отменено: 1.` Повторное включение «Отмена» сбрасывает её расписание и порядок заданий, история отменённой попытки сохраняется.

### Ежедневная выдача

Проводите вдали от московской полуночи. Планировщик проверяет расписание каждые 2 секунды.

7. Основная выдача. Время в «Настройке ежедневной выдачи» по умолчанию 18:00; запись одна, удалить её или добавить вторую нельзя. Установите время на 2–3 минуты позже текущего московского. До него сообщений и сегодняшней отметки нет. После него приходят только A1 и его файлы; в очереди один элемент `open` и один `pending`. Пока ученик не отвечает, новых сообщений нет. После ответов приходят B1 и итог, повторного итога на следующих проходах нет.
8. Ручной запуск до времени выдачи. `/review` сразу выдаёт A1. Не отвечайте и дождитесь выдачи: отметка за сегодня появляется, но A1 не отправляется повторно и очередь не дублируется. Автоматически вопрос не повторяется, по `/review` — повторяется.
9. Смена времени без перезапуска. Перенесите время с будущего на прошедшее: на ближайшем проходе приходит A1. Дальнейшие изменения времени в тот же день новых выдач не создают.
10. Пустая выдача. У ученика без тем и у ученика только с «Пустой» после времени выдачи сообщений нет, отметка за день одна. `/review` у первого сообщает, что заданий нет, у второго показывает уведомление о пропуске и итог.
11. Позднее назначение. Если тема назначена после сегодняшней выдачи, она не попадает в текущую автоматическую очередь. `/review` выдаёт её сразу; без `/review` она придёт со следующей выдачей.
12. Перезапуск и простой. Остановите и запустите процессы при открытом вопросе: тот же ID попытки, повторной автоматической отправки нет. После ответа итог или следующий вопрос восстанавливаются из очереди отправки без нового сообщения ученика. Если планировщик впервые запущен уже после времени выдачи, первый проход сразу формирует выдачу. После нескольких пропущенных дней каждая просроченная тема попадает в очередь один раз.
13. Затянувшееся занятие. В день D ответьте A1 верно и оставьте B1 открытым. В день D+1 после времени выдачи B1 не отправляется повторно, в очередь добавляется одна A. После ответа на B1 приходит A2 (порядок заданий продолжается) в той же сессии. Сроки отсчитываются от московской даты ответа. Без ожидания суток этот сценарий воспроизводит `python -m tests.daily_reviews_demo`.

### Доставка и сбои

14. Заблокируйте бота первым учеником до отправки нового вопроса. Отправка завершается окончательной ошибкой `chat_unavailable`, прогресс не меняется, второй ученик получает свои сообщения. После разблокировки `/start` досылает части той же попытки без новой попытки; `/review` также досылает их и продолжает занятие.
15. Отсутствующий файл. При остановленном планировщике переместите во временном media второй файл снимка A1 и запросите вопрос. Условие и первый файл доставлены, второй получает ошибку `attachment`, ответ ещё не принимается. Верните файл по тому же пути и отправьте `/start`: приходят только недоставленные части.
16. Отключение темы до и во время отправки вопроса отменяет ожидающие части; поздний ответ не меняет прогресс. Часть, уже отправленная в сеть, может прийти, но попытку не восстанавливает.

Временная потеря сети, timeout, RetryAfter, исчерпание повторов, отклонение необрабатываемого события и сбой между отправкой и записью подтверждения проверяются автономными тестами с подменённым транспортом. При моделировании реального сбоя сети повторы идут через 5, 10, 20… секунд, максимум 900, до 10 попыток. При неопределённом результате отправки сообщение может повториться, учебный результат — нет.

### Статистика

17. В статистике ученика видны активные и отключённые темы, ступени, интервалы, даты, текущая доставка и ошибки. Фильтры по теме, результату и периоду открытия (по Москве) и счётчики верных, неверных, открытых и отменённых работают. Страница попытки показывает исходные условие, эталон, ответ и файлы; изменение банка её не меняет.
18. У второго ученика нет чужих попыток и отправок. При истории больше 25 попыток работает пагинация. Без входа страницы ведут на вход в панель, staff без нужных прав получает отказ. Форм редактирования и удаления истории нет.

## Автономные проверки

Без токена и обращений к Telegram:

```bash
.venv-wsl/bin/python manage.py test
.venv-wsl/bin/python manage.py makemigrations --check --dry-run --settings=config.test_settings
.venv-wsl/bin/python -m tests.daily_reviews_demo
.venv-wsl/bin/python -m tests.reliability_demo
.venv-wsl/bin/python -m tests.repetitions_demo
```

Демонстрации используют временные файловые SQLite: многодневное занятие и граница времени выдачи; конкуренция событий, захватов, `/review` и планировщика, перезапуск процесса; применение миграций и переход ступеней. `reliability_demo` также запускается в полном наборе тестов.

## После развёртывания на сервере

Дополнительно к сценариям выше, на сервере (см. [эксплуатацию](amvera-operations.md)):

- HTTPS без циклов перенаправления; ingress заменяет клиентский `X-Forwarded-Proto` — только после этого включается `DJANGO_TRUST_PROXY_HTTPS=true`.
- Вход учителя, CSS/JS панели, защищённое скачивание вложений, `/health/live/` и `/health/ready/`.
- Перед `APP_MODE=run` остановлены все другие экземпляры с тем же токеном, `getMe` успешен, webhook не установлен.
- При обновлении Amvera не появляется второй polling-процесс; блокировка `/data/.runtime.lock` работает на постоянном хранилище.
- Внешний экспорт резервной копии и восстановление на отдельном хранилище.
- Потребление памяти тремя процессами укладывается в тариф.
- Минимум две последовательные ежедневные выдачи без ручного `/review`; продолжение занятия после перезапуска и обновления без двойного изменения прогресса.

## Отчёт приёмки

Для каждого сценария записывайте версию кода, тестового ученика, московскую дату, ID сессии и попытки, прогресс до и после, порядок сообщений, состояние доставки и результат: «пройдено», «ошибка» или «не выполнялось». Автономные проверки отделяйте от действий в Telegram. По завершении остановите процессы; тестовую базу и media в рабочую установку не переносите.
