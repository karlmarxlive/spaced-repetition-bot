# Ручная приёмка этапа 7

Проводите приёмку на отдельной SQLite, media и тестовом боте. Автономные тесты не подтверждают реальную доставку Telegram. Рабочие `.env`, базу, файлы и системные часы не изменяйте для моделирования сбоев.

## Изолированная установка

В PowerShell из корня проекта:

```powershell
$stage7Root = Join-Path $env:TEMP ('stage7-manual-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
New-Item -ItemType Directory $stage7Root | Out-Null
$env:STAGE7_MANUAL_ROOT = $stage7Root
$env:PYTHONPATH = $stage7Root
$env:DJANGO_SETTINGS_MODULE = 'stage7_manual_settings'
$env:TELEGRAM_BOT_TOKEN = ''
$env:TELEGRAM_BOT_USERNAME = ''
$env:DJANGO_DEBUG = 'true'
$env:DJANGO_ALLOWED_HOSTS = 'localhost,127.0.0.1,testserver'
$env:DJANGO_SECRET_KEY = 'isolated-stage7-manual-only'
@'
import os
from pathlib import Path
from config.settings import *
root = Path(os.environ['STAGE7_MANUAL_ROOT'])

MEDIA_ROOT = root / 'media'
STATIC_ROOT = root / 'static'
'@ | Set-Content -Encoding utf8 (Join-Path $stage7Root 'stage7_manual_settings.py')
.\.venv\Scripts\python.exe manage.py shell -c "from django.conf import settings; print(settings.DATABASES['default']['NAME']); print(settings.MEDIA_ROOT)"
```

Проверьте, что оба пути находятся внутри `$stage7Root`, затем:

```powershell
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py migrate --check
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py createsuperuser
.\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

В двух других терминалах задайте тот же путь `$env:STAGE7_MANUAL_ROOT`, `PYTHONPATH`, `DJANGO_SETTINGS_MODULE`, `DJANGO_DEBUG`, `DJANGO_ALLOWED_HOSTS`, `DJANGO_SECRET_KEY`. Введите **отдельный тестовый** токен локально:

```powershell
$env:TELEGRAM_BOT_USERNAME = 'ИмяТестовогоБота'
$stage7Credential = [System.Management.Automation.PSCredential]::new('test-bot', (Read-Host 'Токен тестового бота' -AsSecureString))
$env:TELEGRAM_BOT_TOKEN = $stage7Credential.GetNetworkCredential().Password
Remove-Variable stage7Credential
.\.venv\Scripts\python.exe manage.py shell -c "from django.conf import settings; print(settings.DATABASES['default']['NAME']); print(settings.MEDIA_ROOT)"
```

Панели достаточно имени тестового бота без токена. Бот во втором терминале: `.\.venv\Scripts\python.exe -m bot`. Планировщик в третьем: `.\.venv\Scripts\python.exe manage.py run_scheduler`. Один проход: та же команда с `--once`. Эти команды отправляют настоящие сообщения; одновременно используйте только один polling-процесс. Остановка — Ctrl+C, сетевые сессии должны закрываться.

## Тестовые данные

Создайте курс, темы A и B, задания A1/A2 и B1. Условия `Вопрос A1`, `Вопрос A2`, `Вопрос B1`; эталоны соответственно `11`, `12`, `22`. Добавьте к A1 длинное условие и два небольших файла. Создайте ещё пустую тему и тему отмены. Зарегистрируйте два тестовых аккаунта через разные приглашения; назначьте темы через карточки учеников. Данные второго ученика должны отличаться, чтобы проверить отсутствие смешения истории.

## Реальные Telegram-сценарии

1. `/start` без приглашения нового аккаунта не регистрирует; приглашение регистрирует один раз. Новые `/start` обновляют только Telegram-профиль. Группа и аккаунт бота не расходуют приглашение.
2. `/review` показывает A1 со всеми файлами, без эталона. Статистика карточки показывает попытку и подтверждённую доставку. Новый `/review` показывает ту же попытку; до завершения повторного показа ответ не принимается.
3. Ответьте `11` обычным текстом: результат «Верно.» приходит до B1. Ответьте неверно: ступень B сбрасывается в 0, срок — следующий московский день. Итог относится к этой сессии. Краевые пробелы удаляются, внутренние пробелы и регистр сохраняются.
4. Во время открытой попытки отправьте неизвестную команду, файл с подписью, пустой текст. Прогресс не меняется. Измените текст и эталон банка: открытый вопрос и проверка сохраняют снимок.
5. Отправьте два ответа быстро, до прихода следующего вопроса. Закрывается только первое задание. Явный Telegram reply на предыдущее задание после нового вопроса не должен зачесть новый вопрос. Обычный запоздалый текст, **отправленный уже после нового вопроса**, неоднозначен и трактуется как ответ на текущий вопрос; для точной привязки используйте reply.
6. Остановите и перезапустите процессы до ответа: ID открытой попытки и прогресс сохранены. Повторите после ответа: итог/следующий вопрос восстанавливается из outbox, дополнительный ответ ученика для перехода не требуется. Сбой точно между commit и отправкой воспроизводится автономно, а не ручным угадыванием момента Ctrl+C.
7. Установите время ежедневной выдачи в ближайшем будущем. После него приходит один вопрос. Перезапуск, повторный `--once` и следующий день не пересылают уже доставленное открытое задание. Пустая выдача молчит. Для многодневных правил используйте также прежний [сценарий этапа 6](stage-6-manual-check.md), учитывая новые автоматические повторы.
8. Заблокируйте тестового бота первым учеником **до отправки нового вопроса**. Первый проход сохраняет окончательную ошибку `chat_unavailable`, прогресс не меняется. Второй ученик получает свои сообщения. Разблокируйте бота и отправьте `/review`: восстанавливаются части той же попытки; новая попытка не открывается.
9. Для проверки отсутствующего файла остановите планировщик и только в тестовом media временно переместите второй файл снимка A1 в другой каталог. Запросите вопрос. Подтверждённые условие и первый файл сохраняются, второй файл имеет ошибку `attachment`, вопрос ещё не допускает ответ. Верните файл по **тому же пути** и отправьте `/review`: приходят только неподтверждённые части. Рабочий media не трогайте.
10. Отключите тему перед отправкой и после частичной отправки. Ожидающие части отменяются, поздний ответ не меняет прогресс. Уже находившаяся в сети часть может прийти поздно, но не воскресить попытку. Повторно включите тему: история сохранена, расписание и курсор сброшены; новый показ не использует старую доставку.
11. В карточке ученика откройте статистику: активные/отключённые темы, ступень 0, интервалы, даты, текущая доставка и ошибки. Проверьте фильтры темы, результата, периода открытия по Москве, отдельные количества верных/неверных/открытых/отменённых. Откройте попытку: исходные условие, эталон, ответ и защищённые файлы. Изменение банка не меняет страницу истории.
12. Откройте статистику второго ученика; чужих попыток, счётчиков и отправок нет. Проверьте пагинацию при истории больше 25 попыток. Без входа страницы перенаправляют на Admin login, staff без нужных прав получает отказ. Формы редактирования/удаления истории отсутствуют; подменённый POST проверяется автономно.

Временная сеть, timeout, RetryAfter, исчерпание повторов и авария после принятия Telegram до записи подтверждения проверяются подменённым транспортом. Если моделируете реальный сетевой сбой, делайте это только на отдельной установке: очередная попытка назначается через 5, 10, 20… секунд, максимум 900, не ждёт следующего дня. При неопределённой доставке возможен повтор одной части, без нового учебного результата.

## Автономные симуляции

Без токена и Telegram API:

```powershell
.\.venv\Scripts\python.exe manage.py test
.\.venv\Scripts\python.exe manage.py check --settings=config.test_settings
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run --settings=config.test_settings
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m tests.reliability_demo
```

`manage.py test` использует автономные настройки. Демонстрация создаёт временные файловые SQLite: миграции с нуля и с этапа 6; история с завершёнными, отменённой, открытой и повторными попытками одной темы; сохранность триггеров и ID; продолжение неизвестной старой доставки; конкурентные события, захваты, `/review` и планировщик; блокировка SQLite; новый процесс читает ту же БД и повторяет update без новых эффектов. Успех: `Stage 7 SQLite recovery: OK`. Миграции и `migrate --check` выполняются на этих файлах, не на рабочей БД.

## Обновление рабочей установки

Этот раздел предназначен для осознанного обновления после приёмки. В терминале рабочей установки не должно оставаться `DJANGO_SETTINGS_MODULE=stage7_manual_settings` и переменных тестовой базы: удобнее открыть новый PowerShell. Остановите **все три процесса** перед копированием. Не пересоздавайте окружение, superuser или `.env`.

Из `D:\projects\spaced-repetition-bot`:

```powershell
$stage7Backup = Join-Path $env:USERPROFILE ('spaced-repetition-backups\stage7-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
New-Item -ItemType Directory $stage7Backup | Out-Null
.\.venv\Scripts\python.exe -c "import sqlite3,sys; from pathlib import Path; source=sqlite3.connect(Path('db.sqlite3').resolve().as_uri()+'?mode=ro',uri=True); target=sqlite3.connect(str(Path(sys.argv[1])/'db.sqlite3')); source.backup(target); target.close(); source.close()" $stage7Backup
if ($LASTEXITCODE -ne 0) { throw 'Резервная копия базы не создана' }
if (Test-Path media) { Copy-Item media (Join-Path $stage7Backup 'media') -Recurse -ErrorAction Stop }
.\.venv\Scripts\python.exe manage.py migrate
if ($LASTEXITCODE -ne 0) { throw 'Миграции не применены; процессы пока не запускать' }
.\.venv\Scripts\python.exe manage.py migrate --check
.\.venv\Scripts\python.exe manage.py check
```

Новая миграция — `delivery.0001_initial`; также применяются прежние неприменённые миграции, если они есть. Запустите панель, бот и планировщик обычными командами README. Сравните IDs/статусы/ответы/снимки/даты прогресса до и после; старые открытые вопросы имеют неизвестную доставку, допускают обычный ответ либо повторный показ по `/review`. Массовой рассылки миграция не делает.

Обратная миграция с заполненными транспортными таблицами запрещена. При необходимости отката остановите процессы и восстановите согласованную резервную копию базы и media вместе с подходящей версией кода; это теряет события после момента резервирования. Не называйте удаление транспортных журналов безопасным откатом.

## Отчёт приёмки

Отделите автономные симуляции от реальных Telegram-действий. Ручная приёмка не считается пройденной автоматически после успешных тестов. По завершении остановите процессы; тестовые БД и media не переносите в рабочую установку.
