# План первого запуска на Amvera

Дата исследования: 6 октября 2026 года. Статус: план, без изменений серверного кода и без развёртывания.

Решение пользователя: начать с чистой базы; первая группа — до 10 учеников. Локальные данные остаются на месте. ИИ-помощь и ИИ-проверка отложены до запуска и стабилизации базового учебного цикла.

## Что уже есть

По коду проекта реализованы приглашения, назначения тем, интервалы повторения, ежедневная выдача, сохранённая очередь занятия, проверка короткого текстового ответа по эталону, история ученика и повторная доставка через outbox. Проверка удаляет только пробелы по краям; свободное объяснение и программный код не оцениваются.

Работают три отдельных процесса: Django Admin, `python -m bot` и `python manage.py run_scheduler`. Планировщик проверяет расписание и доставку каждые две секунды; календарные правила используют Europe/Moscow. Отдельный cron для ежедневной выдачи не нужен: этот процесс также восстанавливает доставку сообщений.

В отчёте этапа 7 зафиксированы автономные проверки, но реальная Telegram-приёмка и ожидание следующих календарных суток не выполнены. В рамках этого исследования тесты повторно не запускались.

## Предлагаемая схема

Один проект Amvera, один экземпляр Docker-контейнера, три процесса под общим управляющим процессом:

- Gunicorn с одним worker для Django Admin, слушает `0.0.0.0:8080`.
- Один polling-процесс Telegram.
- Один постоянно работающий планировщик.

Все процессы используют `/data/db.sqlite3` и `/data/media`. Статика админки собирается через collectstatic и раздаётся WhiteNoise. Вложения остаются доступными учителю через существующие защищённые маршруты; публичную раздачу media не включаем.

Это проектное решение для малой первой группы, а не требование Amvera. SQLite сохраняем также потому, что миграции содержат её специфичные триггеры. PostgreSQL потребует отдельной адаптации и проверок. До запуска проверяем конкуренцию ответов, выдачи и сохранения форм админки: известное ограничение текущей версии — возможный SQLite busy / HTTP 500 при сохранении формы.

При обновлении не должны одновременно работать старый и новый polling-процессы. Проверить фактическую стратегию обновления Amvera; для первого релиза предусмотреть контролируемую остановку перед запуском новой версии. Установить один экземпляр недостаточно, если во время обновления платформа временно создаёт второй.

## Требования платформы

- Amvera поддерживает Dockerfile; docker-compose не поддерживается. В `amvera.yml` задаём порт 8080 и монтирование `/data`. [Docker](https://docs.amvera.ru/applications/configuration/docker.html).
- Альтернатива — штатная сборка Python Pip, где версия задаётся тегом Python-образа и можно указать команду запуска. Docker выбран для воспроизводимого окружения с тремя процессами. [Python Pip](https://docs.amvera.ru/applications/environments/python-pip.html).
- База и пользовательские файлы должны находиться в постоянном хранилище по абсолютным путям. Каталог `data` внутри репозитория не равен `/data`. SQLite не требует отдельного сервиса базы данных. [Хранилище](https://docs.amvera.ru/applications/storage.html), [SQLite](https://docs.amvera.ru/databases/sqlite.html).
- Секреты и обычные настройки задаются через окружение Amvera. Токены и рабочий `.env` не входят в образ или Git. [Переменные и секреты](https://docs.amvera.ru/applications/configuration/variables.html).
- HTTPS нужен для панели учителя. Бот сохраняет long polling; входящий webhook не требуется. Настройки домена и маршрутизации сверяем при создании приложения. [Сеть](https://docs.amvera.ru/applications/configuration/network.html).
- Проверки состояния можно настроить через пробы Kubernetes. Нужен контроль трёх процессов: открытый порт панели сам по себе не подтверждает работу выдачи. [Пробы](https://docs.amvera.ru/general/k8sprobe.html).

## Этап 8 — подготовить сборку

1. Добавить Dockerfile, .dockerignore и amvera.yml. Закрепить Python 3.14 с проверенной patch-версией и зависимости. Исключить из сборки .env, локальные базы/бэкапы, media, окружения, логи и Git. Проверить установку закреплённых пакетов в Linux-образе.
2. Добавить серверные настройки: постоянные пути базы/media, DEBUG=false, обязательный SECRET_KEY, конкретные ALLOWED_HOSTS, CSRF-настройки для выбранного HTTPS-домена, secure cookies. Корректность доверия proxy-заголовкам проверить на Amvera, исключить цикл HTTPS-перенаправлений.
3. Добавить Gunicorn и WhiteNoise, collectstatic и проверку загрузки CSS/JS админки при DEBUG=false. Не использовать run_dev.py на сервере: сейчас он запускает runserver на localhost и обрабатывает локальное завершение.
4. Подготовить управляющий процесс: запуск трёх компонентов, обработка SIGTERM/SIGINT, ожидание завершения дочерних процессов, выход с ошибкой при отказе компонента для перезапуска контейнера. Ограничить время остановки; проверить отсутствие оставшихся процессов.
5. Предусмотреть режим первоначальной настройки без polling и рассылки. На чистом /data выполнить миграции и создать учителя безопасной одноразовой процедурой. Ошибка миграции должна предотвращать запуск рабочих процессов. Обновления базы выполнять после остановки процессов и резервирования, никогда на этапе сборки образа.
6. Добавить проверку готовности и признаки активности планировщика; обнаруживать длительные ошибки обработки входящих событий и рост/задержку outbox. Логи направлять в stdout/stderr с существующим скрытием секретов.
7. Подготовить резервирование и восстановление: согласованный снимок SQLite и media, автоматический ежедневный запуск, ограниченное хранение и отдельная копия вне приложения. Для первой версии допустима короткая управляемая пауза записи при создании согласованной копии. Простое копирование открытого файла базы не использовать как гарантированно корректный бэкап.
8. Прогнать автономные тесты и проверки миграций, check --deploy с серверными настройками, сборку контейнера, конкурентный сценарий SQLite и перезапуск с тем же хранилищем. Исправить найденные блокирующие сбои админки, выдачи или ответов.

Результат: готовая к развёртыванию сборка и инструкция первого запуска/обновления/отката. Ориентир по Django: [deployment checklist](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/).

## Этап 9 — приёмка и запуск

1. На изолированной базе и отдельном тестовом боте пройти сценарии docs/stage-7-manual-check.md. Добавить проверку той же серверной сборки при DEBUG=false. Тестовые события не смешивать с рабочей базой.
2. Создать приложение Amvera и выбрать ресурсы по потреблению контейнера в проверке. Группа до 10 учеников не требует горизонтального масштабирования; точный тариф и стоимость зафиксировать по кабинету перед созданием. Не обещать достаточность минимального тарифа без замера памяти трёх процессов.
3. Настроить постоянное хранилище, домен с HTTPS и окружение: TELEGRAM_BOT_TOKEN, TELEGRAM_BOT_USERNAME, DJANGO_SECRET_KEY, DJANGO_DEBUG=false, DJANGO_ALLOWED_HOSTS, серверные пути и HTTPS-параметры, которые появятся на этапе 8. Секреты вводятся вне чата.
4. Начать с новой базы на сервере: применить миграции, создать учителя, вручную заполнить курс, темы, задания с эталонами и вложениями. Текущую локальную базу и media не переносить.
5. До запуска рабочего polling остановить все локальные экземпляры с тем же токеном, проверить getMe и отсутствие конфликтующего webhook. Не отбрасывать ожидающие Telegram updates автоматически. После этого включить бот и планировщик.
6. Создать приглашения, зарегистрировать учеников, назначить пройденные темы и время выдачи по Москве. У каждого назначенного раздела должны быть активные задания с эталонами. Одного успешного запуска контейнера для учебной работы недостаточно.
7. Проверить реальные автоматическую выдачу, ответы обоих типов, итог занятия, следующую дату, вложения и персональную статистику. Перезапустить/обновить приложение посреди занятия и подтвердить продолжение очереди без двойного изменения прогресса.

Результат: работающий бот и панель учителя, доступные независимо от локального компьютера.

## Этап 10 — эксплуатационный пилот

До подключения учеников должны работать резервирование и базовый контроль состояния. Проверить восстановление копии на отдельной установке, сохранив историю, очередь и файлы; не запускать там рабочий polling параллельно оригиналу.

После запуска дождаться как минимум двух последовательных ежедневных выдач без ручного /review, затем наблюдать несколько учебных циклов группы до 10 учеников. Проверить временный сбой Telegram, блокировку бота, восстановление доставки и обновление приложения. При неопределённом результате отправки сообщение может повториться; прогресс повторно изменяться не должен.

Для обновлений описать последовательность: остановка → резервная копия → новая версия и миграции → проверки → запуск. Откат кода не всегда совместим с новой схемой: при необходимости восстанавливать согласованную пару версии и данных с явно отмеченной потерей изменений после копии.

ИИ-проверка и помощь в решении остаются этапами 11–12, со своей приёмкой и правилами влияния подсказок на интервалы.

## MCP и CLI

[MCP Amvera](https://docs.amvera.ru/MCP/doc-mcp-ru.html) — удалённый Streamable HTTP сервер с Bearer-токеном из кабинета. Указаны адреса Москвы `https://openmcp.msk0.amvera.ru/mcp` и Варшавы `https://openmcp.waw0.amvera.ru/mcp`. Доступны операции с проектами, файлами, окружением, доменами, сборкой и логами. Сервер помечен Beta. Подключение полезно для последующего управления инфраструктурой, но не является зависимостью бота. На этом этапе не подключался.

[CLI Amvera](https://docs.amvera.ru/general/cli.html) — альтернативный инструмент управления. Документация указывает установку версии v1.2.2, команды `amvera login`, `amvera help` и `-h` для уточнения синтаксиса. Отмечены статус Beta и повторная авторизация после 24 часов неиспользования. В текущем окружении команда amvera не обнаружена; установка и вход не выполнялись.

Для первого запуска достаточно кабинета и Git. Предлагается хранить код/конфигурацию в Git, а CLI или MCP использовать для настроек, диагностики и перезапуска по необходимости. Токен Amvera не следует добавлять в окружение самого учебного бота.

Также просмотрены [пример Telegram-бота Amvera](https://docs.amvera.ru/general/examples/python-tgbot.html) и [статья о Django](https://habr.com/ru/articles/779544/). Конкретный план основан на текущем коде, официальных требованиях платформы и checklist Django; учебные примеры не покрывают управление всеми тремя процессами этого проекта.
