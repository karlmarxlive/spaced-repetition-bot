## Подтверждённые проблемы и расхождения

1. `config/repetitions.py:13` задаёт `(1, 3, 7, 14, 30, 60)`, то есть `MAX_STEP=6`. Roadmap, README и тесты стандартной цепочки ожидают `(3, 7, 14, 30, 60)` и максимальную ступень 5. При обсуждении оценки пользователь явно подтвердил сохранение текущей цепочки с первым интервалом один день; это решение закреплено в промпте.
2. `modules/repetitions/models.py` использует динамический MAX_STEP, а историческая миграция `0001_initial` и фактическая рабочая таблица содержат CHECK `interval_step <= 5`. Поэтому расчёт допускает ступень 6, которую текущая схема не сохранит. Это следует из кода и прочитанной схемы; запись в рабочую БД для воспроизведения не выполнялась.
3. `makemigrations --check --dry-run` обнаруживает необходимость новой миграции repetitions: изменить валидатор и ограничение диапазона. Файл миграции при проверке не создавался. `migrate --check` проходит, поскольку проверяет применение уже существующих миграций, а не соответствие моделей схеме.
4. README описывает неприменённые миграции этапа 4 как состояние на момент реализации. Сейчас `showmigrations repetitions` показывает обе применёнными; эту историческую оговорку следует отделить от актуальной инструкции.
5. В README зафиксировано отложенное ограничение конкурентной записи админки и бота в SQLite (`database is locked` / HTTP 500). Оно не исправлено и не должно считаться устранённым в результате добавления учебного цикла.

## Точки интеграции этапа 5

- `due_topics(student_id, *, now)` возвращает активные назначения по `(next_review_date, topic.order, topic_id)`, включая темы без активных заданий. Это кандидаты, а не очередь сессии.
- `apply_result(assignment_id, correct, *, now)` изменяет расписание при каждом вызове. Повторное применение не идемпотентно; принять результат ровно один раз должна учебная сессия.
- `assign_topics(student_id, topic_ids, *, now)` — единая транзакция назначения. В неё нужно включить отмену открытой попытки при отключении темы и сброс обхода заданий при повторном включении.
- `Task` сортируется по `(order, pk)`, `TaskAttachment` — по `pk`. Перенос задания между темами допустим; попытка должна хранить исходное назначение и снимок, а не восстанавливать их через актуальный `Task.topic`.
- При замене или удалении записи вложения старый файл остаётся на диске. Поэтому снимок может сохранять упорядоченные storage-пути и имена файлов независимо от живых записей TaskAttachment.
- Синхронные сервисы вызываются из async-обработчиков через `sync_to_async(..., thread_sensitive=True)`; ORM-объекты с ленивыми связями не должны уходить в отправку.
