# Этап 9 — развёртывание и последующая приёмка

Дата: 6 октября 2026 года. По решению пользователя проверки работы перенесены на после развёртывания. Локальная база и media не переносятся. Исходная серверная сборка описана в [инструкции эксплуатации](amvera-operations.md).

## Подготовлено

- Первоначальный режим `APP_MODE=setup`: миграции чистой базы, панель при `DEBUG=false`, без polling и рассылки.
- Одноразовое создание учителя без терминала контейнера через секрет платформы. Пароль проверяется Django, не передаётся дочерним процессам; существующие учителя не изменяются. После создания секрет нужно удалить из Amvera.
- Безопасный запрос токена Amvera и пароля учителя через форму BB. Файл секретов расположен в хранилище треда, вне репозитория и Docker-контекста.

## Текущее состояние развёртывания

Токен Amvera уже предоставлен через переменную окружения `AMVERA_MCP_TOKEN`; повторно вводить его не требуется. Значение не выводится и не загружается в окружение учебного приложения.

Авторизованный запрос MCP `initialize` не получил ответа из-за сетевой ошибки. Повторные соединения с московским endpoint, включая попытку вне sandbox и прямое соединение с определённым DNS адресом, завершились тайм-аутом либо `Connection refused` на TCP 443. Ответ проверки токена не получен; проблема не подтверждает недействительность токена.

По запросу пользователя продолжили через Playwriter и авторизованную консоль Amvera. Создан проект [ege-repeat-bot](https://cloud.amvera.ru/projects/applications/msk0/~/deadkarlmarx/ege-repeat-bot), загружены 118 файлов исходной сборки с сохранением каталогов. Начальный commit Amvera: `877184ba016b1f2a0e3bc5eaf9c086316d838586`. Локальные данные и секреты в загрузку не вошли. Создан HTTPS-домен, сохранено runtime-окружение, в том числе отдельный новый Django SECRET_KEY и одноразовый секрет учителя. Токен Telegram перенесён из локального окружения без вывода значения; в `setup` он не используется.

Сборка через Dockerfile завершена, приложение имеет ID `181042`. API и консоль подтвердили `RUNNING`, один экземпляр; `/health/ready/` ответил `ready: true`. Миграции чистой базы выполнены, учитель создан. Лог подтверждает использование закреплённого Python-образа и `.dockerignore`.

Консоль временами отвечает `Failed to fetch` при обновлении сессии. Через Playwriter выполнялись также браузерные запросы к тем же API, контракты которых прочитаны в исходном JavaScript консоли. Отложенный запрос из старого мастера создания позднее сохранил первоначальные настройки повторно: мастер отменён, домен восстановлен, одноразовые переменные удалены повторно и подтверждено их отсутствие через API. Для применения настроек выполнена остановка до `STOPPED`, 0/0 экземпляров, затем запуск одного экземпляра.

После первого развёртывания выполнены 176 автономных тестов на изолированной базе — `OK`, `makemigrations --check --dry-run` — `No changes detected`. В том числе проверены удаление пароля из окружения до запуска дочерних процессов, создание первого учителя с валидацией и запрет изменения существующего учителя при повторной инициализации. В рабочую базу тестовые события не добавлялись.

При перезапуске обнаружена ошибка очистки временного каталога резервирования на серверном хранилище: `OSError` из `tempfile`/`shutil.rmtree`. Контекстный менеджер `sqlite3.Connection` не закрывал соединения, поэтому открытый snapshot мог оставаться занятым на NFS. В `deploy.backup` добавлено явное закрытие через `contextlib.closing` до очистки/перемещения временных файлов, как для создания копии, так и для восстановления. Регрессионный тест подтверждает закрытие всех трёх соединений; 7 целевых тестов резервирования и инициализации учителя прошли. Исправление подлежит повторному развёртыванию и проверке настоящего перезапуска.

По запросу пользователя настроен Git remote `amvera`: `https://git.amvera.ru/deadkarlmarx/ege-repeat-bot` для fetch и push. `git remote -v` подтвердил настройку; `git ls-remote` не смог соединиться с сервером на порту 443. История Amvera создана отдельно первоначальной загрузкой: перед первым push требуется согласовать истории, без автоматического force push. Повторная загрузка трёх файлов исправления начата через консоль, однако новый коммит и сборка не подтверждены: обновление сессии консоли и прямой запрос API завершились сетевыми тайм-аутами. Последнее подтверждённое состояние приложения — `STOPPED`, 0/0 экземпляров.

## После развёртывания

1. Зафиксировать идентификатор приложения, тариф/стоимость, домен, версию загруженного кода и результат сборки. Убедиться, что одноразовые переменные учителя удалены.
2. Проверить HTTPS и замену proxy-заголовков, вход учителя, CSS/JS, защищённые вложения, liveness/readiness. Доверие `X-Forwarded-Proto` включить только после подтверждения свойств ingress.
3. Выполнить автономные проверки и приёмку [этапа 7](stage-7-manual-check.md) на отдельной базе и отдельном тестовом боте при `DEBUG=false`. Тестовые события не записывать в рабочую базу.
4. Настроить реальный внешний экспорт резервных копий; проверить восстановление на отдельном хранилище без рабочего polling.
5. На сервере заполнить курс, темы, активные задания с эталонами и вложениями. Создать приглашения и назначения для группы до 10 учеников, время выдачи указать по Москве.
6. Перед включением рабочего режима остановить все локальные экземпляры с тем же токеном. Проверить `getMe` и webhook; ожидающие updates не удалять автоматически. Затем остановить контейнер, задать `APP_MODE=run` и запустить единственный экземпляр.
7. Проверить настоящую автоматическую выдачу, верный/неверный ответ, итог, следующую дату, статистику, вложения и продолжение занятия после перезапуска/обновления без двойного изменения прогресса. Замерить память всех трёх процессов и при необходимости изменить тариф.

Сборка или запуск панели сами по себе не означают завершённую учебную приёмку. Следующие ежедневные выдачи требуют наблюдения в реальном времени.
