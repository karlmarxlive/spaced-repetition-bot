# Промпт для реализации этапа 5

Реализуй этап 5 «Полный учебный цикл по команде» в проекте `D:\projects\spaced-repetition-bot` по `roadmap.md`, с учётом текущего `README.md` и фактического кода.

Результат: зарегистрированный ученик в личном чате вызывает `/review`, получает по одному заданию на каждую наступившую тему со всеми вложениями, отвечает текстом, получает результат без раскрытия эталона и автоматически переходит к следующему заданию. В конце бот сообщает краткий итог занятия.

## 2. Границы этапа

Реализуй ручной цикл, минимальную модель занятия/попытки, снимки, круговой выбор, проверку короткого ответа и непосредственную отправку через Telegram.

Не добавляй ежедневный планировщик, настройки времени 18:00, догоняющую выдачу, отдельный процесс, Redis/Celery, ИИ, исполнение кода, подсказки, серверное развёртывание или отдельный фронтенд. Постоянная очередь ежедневной выдачи и её пополнение относятся к этапу 6. Outbox, журнал обработанных Telegram updates, надёжные фоновые retries и административная история относятся к этапу 7.

При этом минимальные инварианты уже обязательны: одна открытая попытка на ученика, закрытая попытка повторно не меняет прогресс, принятый ответ и расписание сохраняются согласованно. Используй короткую общую транзакцию для этого базового перехода; не строй весь механизм надёжности этапа 7 и не заявляй гарантии exactly-once доставки.

## 3. Модель и ответственность модулей

`modules/study_sessions` владеет занятием, текущей попыткой, историей принятых результатов и выбором следующего задания. Добавь Django-приложение и новые миграции. Конкретные имена моделей выбери самостоятельно.

Минимальные данные:

- Занятие ученика: начало, состояние и завершение; достаточно данных для итога и исключения повторной выдачи одной темы в текущем цикле.
- Попытка: занятие/ученик, исходное StudentTopic, ссылка на исходное Task с защитой истории, время открытия и завершения, статус «открыта / верно / неверно / отменена», принятый текст ответа и снимки.
- Снимок содержит исходный текст условия и эталон. Сохрани также исходное название темы для отображения и упорядоченный список путей/имён вложений независимо от дальнейшего изменения TaskAttachment. Эталон доступен только проверяющему коду, не транспортному DTO.
- Состояние обхода заданий по назначению, если его нельзя однозначно получить из истории текущего периода активации. Не храни второй независимый флаг активности темы: источник истины — StudentTopic.is_active.

Ограничениями БД обеспечь отсутствие двух открытых попыток у одного ученика и корректность обязательных связей. Если вводишь модель занятия, исключи два одновременно открытых занятия. Не используй только глобальный словарь или aiogram MemoryStorage как хранилище открытой попытки. Сохранение попытки нужно уже для этапа 5; отдельную долговечную очередь планировщика сейчас не проектируй.

Тема попытки определяется сохранённым назначением, а не текущим Task.topic. Изменение текста, эталона, активности или перенос задания после открытия не меняет текущую попытку и её проверку. Снимок вложений может ссылаться на прежние файлы: текущая политика банка их автоматически не удаляет. Не копируй весь media-каталог и не делай его публичным.

## 4. Прикладной API и очередь ручного цикла

Предоставь операции начала/продолжения review и принятия ответа; при необходимости отдельную операцию получения текущей попытки. Передавай timezone-aware `now` явно. Telegram-объекты не должны попадать в доменные сервисы.

Используй существующие операции:

- `due_topics(student_id, *, now)` возвращает назначения с наступившей московской датой в порядке `(next_review_date, topic.order, topic_id)`, включая темы без активных заданий.
- `apply_result(assignment_id, correct, *, now)` получает только принятый итог от сессии. Проверка и Telegram не вызывают его напрямую.
- `assign_topics(student_id, topic_ids, *, now)` остаётся единым входом назначения и отключения.

Определи и опиши простой алгоритм ручной очереди без модели фонового планировщика. Предпочтительный вариант: при переходе выбирать текущие due-кандидаты, исключая уже обработанные темы занятия; хранить необходимые сведения в занятии/попытках. Не накапливать задания за пропущенные дни. Задокументируй, как учитываются темы, ставшие доступными во время занятия, и последовательно проверь выбранную семантику.

Перед каждой новой попыткой повторно проверяй активность назначения и пригодность задания. Тема без активных заданий пропускается без изменения расписания; она не блокирует остальные темы и не вызывает бесконечный цикл. Ученик получает понятное сообщение, а итог отдельно учитывает пропуски. Если вся очередь пуста или все темы пропущены, ответ всё равно осмысленный.

При существующей открытой попытке `/review` продолжает её: повторно показывает тот же снимок и вложения, не создаёт новую попытку и не сдвигает порядок. Без ответа прогресс не меняется, в том числе после полуночи. Открытая попытка должна читаться из БД при новом запуске процесса; полная матрица аварийного восстановления остаётся этапу 7.

## 5. Круговой выбор заданий

Для каждой пары «ученик — тема» выдавай активные Task по `(order, pk)`, с возвратом к первому после последнего. Единственное активное задание повторяется в следующих циклах. Разные ученики и темы независимы.

Продвигай обход после завершённой учебной попытки, включая неверный ответ. Повторная отправка текущего вопроса обход не сдвигает. Отключение задания влияет на будущие открытия, но не отменяет уже открытое. Опиши устойчивое поведение при добавлении, перестановке и переносе заданий, включая исчезновение последнего выбранного задания из исходной темы. Проверь минимум перенос и деактивацию между двумя выдачами.

При повторном включении StudentTopic начинается новый обход с первого активного задания; старые попытки сохраняются. Не используй старую историю для продолжения прежнего обхода после сброса назначения.

## 6. Проверка и принятие ответа

В `modules/checking` создай простой интерфейс, возвращающий «верно / неверно / проверка недоступна» и необязательный фидбек. Точная текстовая реализация сравнивает ответ со снимком эталона после удаления только краевых пробельных символов у обеих строк (`strip()`). Не меняй регистр, внутренние пробелы, пунктуацию, ведущие нули или числовой формат; никакого числового парсинга или Unicode-нормализации.

Пустой после strip ответ считай отсутствием учебного ответа: попроси текст, не закрывая попытку. Входящие команды, фото, документы, стикеры, голосовые сообщения и подписи к ним не являются неверным ответом. Команды обрабатывай до общего текстового обработчика; неизвестная команда тоже не должна попасть в проверку.

Только обычный текст от зарегистрированного ученика в личном чате может завершить его открытую попытку. Если попытки нет, предложи `/review`. Не доверяй имени/username для идентификации; используй Telegram ID и проверяй принадлежность попытки.

В одной транзакции перечитай состояние, сохрани принятый ответ/результат и вызови apply_result для исходного назначения. Повторное принятие уже закрытой или отменённой попытки не вызывает новый переход. «Проверка недоступна» и техническая ошибка не должны становиться неверным ответом или изменять расписание.

Сначала сообщи «верно» или «неверно» без эталона, затем отправь следующее задание. Неверный ответ завершает попытку; немедленно повторять тот же вопрос для исправления нельзя. Следующий срок рассчитывает существующий движок от московской даты принятого ответа. По завершении выдай количество принятых ответов, верных и неверных; отдельно — пропущенные/отменённые темы, если они были.

## 7. Отключение темы

Расширь транзакцию assign_topics: отключение назначения сразу отменяет открытую попытку по нему без применения результата; ожидающие темы больше не выдаются. Согласуй зависимость модулей без циклических импортов и спрятанных сетевых действий в сигналах.

Поздний ответ на отменённую попытку не меняет прогресс и не должен автоматически считаться ответом на ещё не показанное следующее задание. Объясни отмену, после чего продолжи оставшуюся очередь или заверши занятие. `/review` также должен корректно продолжать после отмены. При ошибке отмены транзакция назначения откатывается целиком.

После повторного включения сбрасываются расписание существующим API и обход заданий; отменённая попытка не воскресает. Неизменённое сохранение формы ученика не сбрасывает сессию, даты или обход.

## 8. Telegram и доставка

Оставь handlers тонкими; вызывай синхронные транзакционные сервисы через `sync_to_async(..., thread_sensitive=True)`. Возвращай материализованные DTO без ленивого ORM и без эталона. В `modules/delivery` выдели непосредственную отправку снимка, результата и итога.

Условие отправляется полностью, затем все вложения в исходном порядке. Для произвольных файлов допустима последовательная отправка документами, включая изображения; не вводи обязательный альбом. Используй локальные файлы, а не защищённые admin-URL. Учти длинные условия: разбивай на допустимые части без потери текста; отключи разметку или корректно экранируй пользовательское содержимое. Сопровождение вложений не должно содержать эталон.

Сетевые вызовы выполняй после завершения транзакции. Ошибка отправки/отсутствующий файл не являются ошибкой ученика; не закрывай попытку и не создавай новую при повторном `/review`. При частичной доставке повторная команда может повторить сообщения той же попытки — это приемлемое ограничение этапа. Автоматические фоновые retries не добавляй.

Обнови тексты `/start`: вместо «Выдача заданий появится позже» объясни `/review`. Сохрани регистрацию, приглашения и запрет учебных операций в группах. Неподдерживаемый ввод сопровождай короткой подсказкой без изменения попытки. Секреты, эталоны и полные тексты ответов не выводи в прикладные логи.

## 9. Проверки и миграции

Все проверки автономны, без токена и внешней сети; используй существующие config.test_settings, временный MEDIA_ROOT и подменённый транспорт aiogram. Не скрывай исходные падения: сначала устрани несогласованность политики, затем проверь регрессии и новый цикл.

Обязательные сценарии:

1. Полный цикл нескольких тем: верный, неверный, следующий вопрос, итог; эталон отсутствует во всех исходящих сообщениях.
2. Пустая очередь, только будущие/отключённые темы, тема без заданий, только неактивные задания, несколько просроченных дней без дубликатов.
3. Повтор `/review`, текст без текущей попытки, команды (включая неизвестные), пустой текст, неподдерживаемые вложения и подписи, группа и незарегистрированный пользователь.
4. Точная проверка: краевые пробелы, регистр, внутренние пробелы, `01` против `1`, `1.0` против `1`; недоступная проверка не меняет прогресс.
5. Круговой порядок и возврат к первому, единственное задание, независимость учеников/тем, изменение активности и перенос задания.
6. Снимки текста, эталона, исходной темы и списка файлов после правок банка; все вложения в правильном порядке, одинаковые имена, длинный текст, отсутствующий файл и ошибка транспорта.
7. Ответ после московской полуночи; отсутствие ответа не меняет дату. Повторное чтение открытой попытки через новый экземпляр сервиса возвращает тот же вопрос.
8. Отключение темы через существующую форму админки отменяет попытку, поздний ответ не меняет прогресс; повторное включение сбрасывает обход, история остаётся. Неизменённое сохранение ничего не сбрасывает.
9. Повторное завершение той же попытки не меняет расписание дважды; откат при ошибке между записью ответа и прогресса. Ограничение одной открытой попытки проверяется БД. Не заявляй полную защиту от повторных Telegram updates как выполненный этап 7.
10. Миграции на пустой временной БД и обновление временной копии структуры этапа 4 с фикстурами: данные материалов, пользователей, назначений, прогресса и ссылки вложений сохраняются. При шести интервалах проверь сохранение ступени 6 и отклонение 7 непосредственно БД. Повтор migrate не сбрасывает данные.

Выполни из существующего окружения:

```powershell
.\.venv\Scripts\python.exe manage.py test
.\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe -m pip check
```

Проверь `migrate --check` отдельно на временной мигрированной БД и, только как диагностику, на рабочей. Неприменённые новые миграции рабочей установки явно перечисли; не применяй их сам. На Windows закрывай SQLite-соединения до удаления временных каталогов. Не смешивай успешный dry-run модели и факт обновления рабочей БД.
